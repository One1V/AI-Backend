# What can we infer from that the website is hosted on localhost:5000 but we can also acceess it with localhost only?


---

## Without Nginx (Development)

Suppose your frontend and backend are running separately.

* Frontend (Vite/React): `http://localhost:5173`
* Express Backend: `http://localhost:5000`

Your frontend must call:

```js
fetch("http://localhost:5000/api/message")
```

because the browser knows the backend is on port 5000.

**Flow:**

```text
Browser
   │
   ├── http://localhost:5173  → Frontend
   │
   └── http://localhost:5000/api/message → Express
```

Since the ports are different, this is a **cross-origin request**, so you usually need CORS.

---

# With Nginx (Production)

Imagine your website is:

```
https://youtube.com
```

There is **no `:5000` visible**.

Why?

Because **Nginx is standing in front of everything.**

```
                Internet
                    │
                    ▼
            youtube.com
                    │
               Nginx (Port 80/443)
               /            \
              /              \
      Frontend Files      Express API
```

Now your browser only knows one address:

```
https://youtube.com
```

When JavaScript executes

```js
fetch("/api/message")
```

the browser automatically expands it to

```
https://youtube.com/api/message
```

Notice it did **not** add

```
:5000
```

because it always contacts the **same server that served the webpage**.

---

## What does Nginx do?

Suppose you configure Nginx like this:

```nginx
location / {
    root /var/www/html;
}

location /api/ {
    proxy_pass http://localhost:5000;
}
```

Now the flow becomes

```
Browser
      │
      │ GET /
      ▼
Nginx
      │
      ├── Returns index.html
      │
      ▼
Browser loads JavaScript
      │
      │ fetch("/api/message")
      ▼
Nginx
      │
      │ sees "/api"
      ▼
Express (localhost:5000)
      │
      ▼
{ "message": "Hello" }
      │
      ▼
Nginx
      │
      ▼
Browser
```

The browser **never talks directly to Express**.

---

# Why no `localhost:5000`?

Because `"/api/message"` is a **relative URL**.

If your page came from

```
https://mywebsite.com
```

then

```js
fetch("/api/message")
```

becomes

```
https://mywebsite.com/api/message
```

If your page came from

```
http://localhost:3000
```

it becomes

```
http://localhost:3000/api/message
```

The browser automatically uses the **same protocol, host, and port** as the current page.

---

# Why is this better?

### Without Nginx

```js
fetch("http://localhost:5000/api/message")
```

Problems:

* Exposes backend address.
* Requires CORS if frontend and backend use different origins.
* If backend port changes, frontend code must change.

---

### With Nginx

```js
fetch("/api/message")
```

Advantages:

* No CORS needed (same origin).
* Backend can move to another port or even another machine without changing frontend code.
* Nginx decides where to forward requests.

# Real Example: YouTube

Suppose you open:

```
https://youtube.com
```

When you click a video, the browser might internally request:

```
GET /api/video/abc123
```

The browser sends that request to:

```
youtube.com
```

**not** to

```
backend-server-42:8080
```

Nginx (or another reverse proxy/load balancer) receives the request and forwards it to one of many backend servers.

```
Browser
    │
    ▼
youtube.com
    │
    ▼
Nginx
    │
 ┌──┼──────────────┐
 ▼  ▼              ▼
Express #1    Express #2    Express #3
```

The browser has no idea which backend server handled the request. It only knows **youtube.com**.

---

### Interview takeaway

If asked, **"Why do we use `fetch("/api/message")` instead of `fetch("http://localhost:5000/api/message")` in production?"**, a strong answer is:

> We use a relative URL because the browser sends the request to the same origin that served the webpage. A reverse proxy like Nginx receives the request and forwards `/api/*` to the Express backend. This hides backend infrastructure, avoids CORS issues, and lets us change backend servers or ports without modifying frontend code.
