# **Why does your Node.js server stop when you close SSH?**

⭐ **Importance:** ⭐⭐⭐⭐⭐ (One of the Most Important Deployment Concepts)

This is the point where Linux processes meet **real backend deployment**.

---

# The Situation

Suppose you rent an Ubuntu server.

You connect using SSH:

```bash
ssh ubuntu@your-server-ip
```

Now you're inside the server.

You start your backend:

```bash
node server.js
```

Output:

```text
Server running on port 5000
```

Everything works.

Users can access:

```text
Internet

↓

Ubuntu Server

↓

Node.js

↓

Express

↓

Response
```

---

# Then You Disconnect

You type:

```bash
exit
```

or simply close your terminal.

A few minutes later...

🚨 Users report:

> "The website is down."

Why?

---

# Understanding SSH

SSH gives you a **terminal session** on the remote server.

Think of it like this:

```text
Your Laptop

↓

SSH Connection

↓

Ubuntu Terminal

↓

node server.js
```

Your Node.js process is attached to **that terminal session**.

---

# What Happens When SSH Closes?

When you disconnect:

```text
Laptop

↓

SSH Closed

↓

Terminal Ends

↓

Foreground Process Ends

↓

Node Server Stops
```

Linux assumes:

> "The terminal that started this process no longer exists."

So it terminates processes attached to that terminal.

---

# Visual Flow

```text
SSH Connected

↓

node server.js

↓

Node Process Running

↓

Close SSH

↓

Terminal Dies

↓

Node Process Dies
```

---

# Real Example

You deploy an Express API.

Run:

```bash
node server.js
```

Open the API:

```text
http://your-server-ip:5000
```

Works perfectly.

Now disconnect SSH.

Try again.

```text
This site can't be reached
```

The process is gone.

---

# Why Doesn't This Happen on Vercel or Render?

Platforms like Vercel and Render **don't keep your app tied to an SSH terminal**.

Instead, they use **process managers** and orchestration systems that keep your application running independently.

That's why your app stays online even when you're not connected.

---

# How Do We Fix This?

Instead of running:

```bash
node server.js
```

Use a **process manager** like:

* PM2 ✅ (Most common for Node.js)
* `systemd`
* Docker
* Kubernetes (large-scale deployments)

These tools:

* Start your app.
* Keep it running after SSH disconnects.
* Restart it if it crashes.
* Start it automatically after a server reboot.

---

# Example with PM2

Instead of:

```bash
node server.js
```

You run:

```bash
pm2 start server.js
```

Now:

```text
SSH Disconnect

↓

PM2 Still Running

↓

Node Process Continues

↓

Website Stays Online
```

PM2 becomes the parent process responsible for your application.

---

# Interview Question

### Q1. Why does a Node.js server stop when you close SSH?

**Answer:**

Because the server was started as a foreground process attached to the SSH terminal. When the SSH session ends, the terminal closes and Linux terminates processes associated with it unless they are managed independently.

---

### Q2. How do you keep a Node.js server running after SSH disconnects?

**Answer:**

Use a process manager such as **PM2** or a service manager like **systemd**. These tools keep the application running independently of the SSH session and can automatically restart it if it crashes.

In Linux, there are mainly **3 useful categories of users** to understand:

### 1. Root user

The **root** user is the administrator with almost unlimited privileges.

```text
root
 ↓
Can read/write/delete most files
Can install software
Can create/delete users
Can change permissions
Can manage services
```

Example:

```bash
sudo apt update
```

`sudo` lets a normal user temporarily perform an operation with elevated/root privileges.

---

### 2. Regular user

This is the normal account you use for everyday work.

Example:

```text
ayush
```

It can:

* Create files in its home directory
* Run programs
* Modify its own files
* Usually cannot modify protected system files directly

For example:

```bash
/home/ayush/
```

---

### 3. System/service user

These accounts are created mainly for **running services/applications**, not for humans.

Examples you may encounter:

```text
www-data
mongodb
redis
```

For example, Nginx may run under:

```text
www-data
```

A Node application could also be configured to run under a dedicated user such as:

```text
nodeapp
```

This is a **security practice**: if the application is compromised, it doesn't automatically have root-level access to the entire server.

---

## Very important for your VPS project

Imagine:

```text
Linux VPS
│
├── root          → Server administrator
│
├── ayush         → You
│
└── nodeapp       → Node.js application
```

Then:

```text
ayush
  ↓
Can manage his own files

nodeapp
  ↓
Can access only the files/resources it needs

root
  ↓
Can manage everything
```

This connects directly to your `.env` question.

If `.env` is:

```text
-rw------- nodeapp nodeapp .env
```

then the Node application running as `nodeapp` can read it, while other ordinary users cannot.

> **Regular user = human account**
> **System/service user = account used to run services securely**
