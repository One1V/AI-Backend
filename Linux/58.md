
# Q58 — DNS from a Backend Engineer's Perspective

**DNS = Domain Name System.**

Its main job is to translate a human-readable domain name into an IP address.

```text
google.com
    ↓
IP address
    ↓
Server
```

Think of DNS as the **internet's phonebook**.

---

## 1. Why do we need DNS?

Imagine your VPS has:

```text
203.0.113.25
```

You could tell users:

```text
http://203.0.113.25
```

But that's difficult to remember.

Instead, you buy a domain:

```text
myapp.com
```

DNS connects:

```text
myapp.com
     ↓
203.0.113.25
```

So users can access:

```text
https://myapp.com
```

---

# 2. Real MERN deployment

Suppose you've deployed your backend on a VPS:

```text
VPS
Public IP:
203.0.113.25
```

You own:

```text
myapp.com
```

You configure DNS:

```text
myapp.com
    ↓
203.0.113.25
```

Then the user's request looks conceptually like:

```text
Browser
   ↓
myapp.com
   ↓
DNS lookup
   ↓
203.0.113.25
   ↓
VPS
   ↓
Nginx
   ↓
Express
```

DNS's job is primarily the **domain → IP** part.

---

# 3. What happens when you type a URL?

Suppose you type:

```text
https://myapp.com
```

The browser needs to know:

> "What IP address belongs to `myapp.com`?"

It performs DNS resolution.

Conceptually:

```text
Browser
   ↓
DNS resolver
   ↓
DNS servers
   ↓
203.0.113.25
   ↓
Browser connects to server
```

Then HTTPS communication happens.

---

# 4. DNS does NOT send your HTTP request

This distinction is important.

DNS does:

```text
myapp.com
    ↓
IP address
```

It doesn't do:

```text
myapp.com
    ↓
Express
    ↓
MongoDB
```

Instead:

```text
DNS
 ↓
Find IP
 ↓
Browser connects to IP
 ↓
HTTP/HTTPS request
 ↓
Nginx
 ↓
Express
```

---

# 5. Common DNS records

As a backend engineer, you should know a few important record types.

### A record

Maps a domain to an IPv4 address.

```text
myapp.com
    ↓
203.0.113.25
```

Example:

```text
A → 203.0.113.25
```

---

### AAAA record

Maps a domain to an IPv6 address.

```text
myapp.com
    ↓
IPv6 address
```

---

### CNAME

Creates an alias pointing to another hostname.

For example:

```text
www.myapp.com
      ↓
myapp.com
```

Or:

```text
api.myapp.com
      ↓
some-service.example.com
```

A CNAME points to a **hostname**, not directly to an IP address.

---

### MX

Used for email routing.

```text
myapp.com
    ↓
MX
    ↓
Mail server
```

You don't need to deeply learn MX for backend deployment, but know what it is.

---

# 6. Subdomains

This is very useful for your backend projects.

You could have:

```text
myapp.com
```

for your frontend.

And:

```text
api.myapp.com
```

for your backend.

DNS could be:

```text
myapp.com
    ↓
Frontend server

api.myapp.com
    ↓
Backend VPS
```

Then:

```text
Browser
   ↓
https://api.myapp.com/users
   ↓
DNS
   ↓
Backend VPS IP
   ↓
Nginx
   ↓
Express
```

# 7. DNS and your previous concepts

You're now connecting several concepts:

```text
Domain
   ↓
DNS
   ↓
IP address
   ↓
Port
   ↓
Nginx
   ↓
Express
```

For example:

```text
https://api.myapp.com
        ↓
       DNS
        ↓
203.0.113.25
        ↓
      :443
        ↓
      Nginx
        ↓
 localhost:5000
        ↓
     Express
```

This is a **real deployment architecture**.

---

# 8. How can you test DNS from Linux?

One simple command is:

```bash
nslookup myapp.com
```

You may see:

```text
Name:    myapp.com
Address: 203.0.113.25
```

Another useful command is:

```bash
dig myapp.com
```

`dig` gives more detailed DNS information.

For your current level:

```text
nslookup → simple DNS lookup
dig      → detailed DNS troubleshooting
```

---

# 9. DNS caching

DNS responses can be cached.

For example:

```text
Browser
   ↓
Local DNS cache
   ↓
DNS resolver
```

This improves performance because the system doesn't need to perform a complete lookup every time.

DNS records have a **TTL (Time To Live)** that controls how long resolvers may cache the response.

You don't need to go deeply into DNS caching yet, but understand the concept.

---

# 10. What happens if DNS is wrong?

Suppose your VPS IP is:

```text
203.0.113.25
```

but your DNS record points to:

```text
203.0.113.99
```

Then:

```text
myapp.com
    ↓
203.0.113.99 ❌
```

Your browser will connect to the wrong destination.

Your Express application might be perfectly healthy, but the domain won't reach it.

This is why DNS is one of the first things to check when a newly deployed domain doesn't work.

# 🧠 Interview Questions

### "What is DNS?"

> **DNS is a distributed naming system that translates domain names into IP addresses and provides other domain-related records.**

### "What is an A record?"

> **An A record maps a domain or hostname to an IPv4 address.**

### "What is CNAME?"

> **A CNAME record maps one hostname to another hostname.**

### "Does DNS handle HTTP requests?"

> **No. DNS resolves the hostname to an IP address. The browser then establishes a network connection to that server and sends the HTTP/HTTPS request.**
