
# Q66 — What are Environment Variables?

Environment variables are **key-value pairs provided to a process through its environment**.

For backend development, they're commonly used to store **configuration that should not be hard-coded into your source code**, such as:

* Database connection strings
* API keys
* JWT secrets
* Application port
* Environment (`development` / `production`)

---

## 1. Real backend example

Suppose your Express application needs MongoDB:

```text
MongoDB connection:
mongodb+srv://user:password@cluster...
```

❌ Don't put it directly in your code:

```javascript
mongoose.connect("mongodb+srv://user:password@cluster...");
```

Instead:

```text
Environment
    ↓
MONGO_URI=...
    ↓
Node.js
    ↓
process.env.MONGO_URI
    ↓
MongoDB
```

Your code becomes:

```javascript
mongoose.connect(process.env.MONGO_URI);
```

---

# 2. What is an environment variable?

It's simply:

```text
NAME=VALUE
```

For example:

```bash
PORT=5000
```

or:

```bash
NODE_ENV=production
```

or:

```bash
JWT_SECRET=mySuperSecret
```

The operating system makes these values available to programs running in that environment.

---

# 3. Simple Linux example

On your Linux VPS, run:

```bash
export PORT=5000
```

Now:

```bash
echo $PORT
```

returns:

```text
5000
```

The `$` means:

> Give me the value of the `PORT` environment variable.

---

# 4. Node.js can read it

Suppose you have:

```javascript
console.log(process.env.PORT);
```

and your Linux environment contains:

```text
PORT=5000
```

Node.js can access it:

```text
Linux environment
       ↓
PORT=5000
       ↓
Node.js process
       ↓
process.env.PORT
       ↓
"5000"
```

So:

```javascript
console.log(process.env.PORT);
```

prints:

```text
5000
```

---

# 5. Real Express example

You might write:

```javascript
const express = require("express");

const app = express();

const PORT = process.env.PORT || 5000;

app.listen(PORT, () => {
    console.log(`Server running on ${PORT}`);
});
```

Now:

### Development

No `PORT` variable:

```text
process.env.PORT
        ↓
undefined
        ↓
5000
```

### Production

You configure:

```text
PORT=5000
```

Then:

```text
process.env.PORT
        ↓
5000
```

---

# 6. `.env` files

In Node.js projects, you commonly see:

```text
.env
```

Example:

```text
PORT=5000
MONGO_URI=mongodb+srv://...
JWT_SECRET=some-secret
```

Then with the `dotenv` package:

```javascript
require("dotenv").config();
```

your application can access them through:

```javascript
process.env.MONGO_URI
process.env.JWT_SECRET
process.env.PORT
```

---

# 7. Important distinction: `.env` vs environment variable

This is something you should understand clearly.

A `.env` file is **just a file**.

For example:

```text
.env
```

contains:

```text
PORT=5000
```

When you use something like `dotenv`, those values are loaded into the Node.js process environment.

Conceptually:

```text
.env file
   ↓
dotenv
   ↓
process.env
   ↓
Node.js application
```

So `.env` itself isn't a special Linux mechanism.

---

# 8. Why are environment variables useful?

Imagine your code is on GitHub.

You don't want:

```javascript
const JWT_SECRET = "my-real-secret";
```

because anyone who gets access to the repository could potentially see it.

Instead:

```javascript
const JWT_SECRET = process.env.JWT_SECRET;
```

and configure the actual value separately.

Your repository can contain:

```text
server.js
package.json
README.md
```

but not the real secrets.

---

# 9. Development vs production

This becomes especially important now that you're learning Linux deployment.

### Local machine

You might have:

```text
.env
```

```text
PORT=5000
MONGO_URI=...
NODE_ENV=development
```

### VPS

The production server might have:

```text
PORT=5000
MONGO_URI=production-database
NODE_ENV=production
```

Same application code:

```javascript
process.env.MONGO_URI
```

Different environment.

That's a major advantage.

---

# 10. Your deployment architecture

This connects directly to your previous Linux permissions question.

Suppose:

```text
Linux VPS
│
├── Application
│      ↓
│   Node.js
│      ↓
│ process.env.MONGO_URI
│
└── Environment/configuration
       ↓
    secret value
```

When Node starts, it gets its environment.

A normal internet user doesn't automatically get access to the server's environment just because they can access your website.

For example:

```text
User's Browser
      ↓
https://myapp.com
      ↓
Nginx
      ↓
Express
      ↓
process.env.JWT_SECRET
```

The browser doesn't automatically receive:

```text
JWT_SECRET=...
```

unless **your application accidentally exposes it**.

---

# 11. Very important security point

Environment variables are **not magically secure**.

If your application does:

```javascript
res.json(process.env);
```

you could expose your environment variables to users.

Similarly, if you log secrets:

```javascript
console.log(process.env.JWT_SECRET);
```

you've exposed them in logs.

So the correct principle is:

> **Keep secrets out of source code and expose them only to the processes that need them.**

---

# 12. Interview answer

If asked:

> **"What are environment variables?"**

A strong answer:

> **"Environment variables are key-value configuration values provided to a process by its environment. They're commonly used for configuration and secrets such as database URLs, API keys, JWT secrets, ports, and environment-specific settings, so these values don't have to be hard-coded into the application."**

If asked:

> **"Why use environment variables?"**

Say:

> **"They separate configuration and secrets from application code, making the same codebase easier to run across development, testing, and production environments."**
