# Q71 — Why should you keep secrets out of source code?

This is extremely important for backend development and deployment.

Suppose your Express application needs:

```text
MongoDB password
JWT secret
API key
Cloud credentials
Payment gateway secret
```

You might be tempted to write:

```javascript
const JWT_SECRET = "mySuperSecret123";
```

**Don't do this.**

---

## 1. The problem with hard-coding secrets

Suppose your project is:

```text
my-backend/
├── server.js
├── package.json
└── controllers/
```

And you write:

```javascript
const MONGO_URI =
  "mongodb+srv://ayush:password123@cluster...";
```

Then you push the project:

```bash
git add .
git commit -m "backend"
git push
```

Now the secret can become part of your Git history.

Even if you later delete the line, the secret may still exist in **previous commits**.

---

# 2. Real-world deployment flow

You want:

```text
GitHub
   ↓
Application code
   ↓
Linux VPS
   ↓
Node.js
   ↓
MongoDB
```

The repository should contain:

```text
server.js
package.json
controllers/
models/
```

but **not your production secrets**.

Instead:

```text
GitHub
   ↓
Code only

Linux VPS
   ↓
Production configuration/secrets
   ↓
Node.js
```

---

# 3. Use environment variables

Instead of:

```javascript
const JWT_SECRET = "abc123";
```

use:

```javascript
const JWT_SECRET = process.env.JWT_SECRET;
```

Then provide the value separately.

For example:

```env
JWT_SECRET=abc123
```

Conceptually:

```text
              GitHub
                │
                │ code
                ▼
             Linux VPS
                │
        ┌───────┴────────┐
        │                │
      Code            Secrets
        │                │
        └───────┬────────┘
                ↓
             Node.js
                ↓
         process.env.JWT_SECRET
```

---

# 4. What kinds of things are secrets?

Typical examples:

```text
JWT_SECRET
MONGO_URI
STRIPE_SECRET_KEY
AWS_ACCESS_KEY
AWS_SECRET_KEY
DATABASE_PASSWORD
API_KEY
```

Not everything in configuration is necessarily a secret.

For example:

```text
PORT=5000
NODE_ENV=production
```

are configuration values but generally aren't sensitive secrets.

---

# 5. `.env` and `.gitignore`

During development you might have:

```text
.env
```

containing:

```env
PORT=5000
MONGO_URI=...
JWT_SECRET=...
```

Then add:

```text
.env
```

to:

```text
.gitignore
```

So:

```text
Local machine
│
├── .env        ← contains real values
├── server.js
└── package.json
       │
       ▼
     Git
       │
       ▼
    GitHub
       │
       ├── server.js
       └── package.json
     
       ❌ .env
```

---

# 6. What about `.env.example`?

You can commit:

```text
.env.example
```

with:

```env
PORT=5000
MONGO_URI=
JWT_SECRET=
```

This tells another developer:

> "These variables are required."

But it doesn't expose the actual values.

---

# 7. What happens on your VPS?

Suppose your production server has:

```text
/home/ubuntu/myapp
```

Your application can receive:

```text
MONGO_URI=production_database
JWT_SECRET=production_secret
```

Then:

```javascript
mongoose.connect(process.env.MONGO_URI);
```

The source code stays the same between:

```text
Development
```

and:

```text
Production
```

Only the configuration changes.

That's one of the biggest reasons environment variables are useful.

---

# 8. What if a secret gets pushed accidentally?

This is important:

**Don't assume deleting the secret from the latest file fixes the problem.**

If you pushed:

```text
JWT_SECRET=abc123
```

to GitHub, treat it as **compromised**.

You should:

1. Revoke/rotate the secret.
2. Remove it from the repository/history as appropriate.
3. Replace it with a new secret.
4. Update the production environment.

For example, if a database password was exposed:

```text
Old password
     ↓
Compromised
     ↓
Change password
     ↓
Update server configuration
```

---

# 9. Why this matters specifically for your Linux deployment

You're moving from:

```text
Render/Vercel
```

toward understanding:

```text
Your own VPS
     ↓
Linux
     ↓
Node.js
     ↓
Nginx
```

When you manage the server yourself, **you become responsible for managing configuration and secrets properly**.

For example:

```text
Linux VPS
│
├── Application code
├── Nginx configuration
├── Environment/configuration
└── Secrets
```

You shouldn't put secrets into:

```text
GitHub
```

just because your server needs them.

---

# 🧠 Interview Answer

If asked:

> **"Why shouldn't secrets be stored in source code?"**

Give this answer:

> **"Because source code is often stored in version control and shared with other developers or systems. Hard-coding secrets can expose credentials through repositories and Git history. Instead, sensitive configuration should be supplied through environment variables or a dedicated secret-management system and rotated if exposed."**

That's a strong backend interview answer.
