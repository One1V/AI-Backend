
# Q73 — Where are Linux logs stored?

Logs are records of what happens on your Linux system.

For a backend engineer, logs are extremely important because when something goes wrong in production, you often **can't just look at your code and know the problem**.

You inspect the logs.

---

# 1. Where are Linux logs?

A major location is:

```text
/var/log/
```

Check it:

```bash
ls /var/log
```

You may see files/directories such as:

```text
/var/log/
├── auth.log
├── syslog
├── kern.log
├── nginx/
├── apt/
└── ...
```

The exact files depend on your Linux distribution and configuration.

---

# 2. Why `/var/log`?

Remember the Linux filesystem hierarchy from Q8:

```text
/
├── etc
├── home
├── usr
├── var
└── tmp
```

`/var` contains **variable data**—data that changes while the system operates.

Therefore:

```text
/var
 ↓
/var/log
 ↓
Log files
```

---

# 3. System logs

For example, Ubuntu may have:

```text
/var/log/syslog
```

You can inspect it with:

```bash
sudo less /var/log/syslog
```

Or:

```bash
sudo tail /var/log/syslog
```

To continuously watch new entries:

```bash
sudo tail -f /var/log/syslog
```

Remember what you learned in Q22:

```text
tail -f
   ↓
Keep watching a file
   ↓
Display new lines as they're added
```

---

# 4. Authentication logs

On systems that use traditional auth logs, you may have:

```text
/var/log/auth.log
```

It contains authentication/security-related events.

For example, SSH activity can produce entries there.

You can inspect:

```bash
sudo tail /var/log/auth.log
```

This can be useful when debugging:

```text
SSH login problems
sudo activity
authentication failures
```

---

# 5. Nginx logs

This is particularly relevant to your deployment project.

Nginx commonly stores logs under:

```text
/var/log/nginx/
```

Check:

```bash
ls /var/log/nginx
```

You may find:

```text
access.log
error.log
```

---

## `access.log`

Records HTTP requests handled by Nginx.

For example, conceptually:

```text
GET /api/users
POST /login
GET /style.css
```

You can watch it:

```bash
sudo tail -f /var/log/nginx/access.log
```

---

## `error.log`

Contains Nginx errors and diagnostic information.

Watch it:

```bash
sudo tail -f /var/log/nginx/error.log
```

This is incredibly useful when your Nginx configuration isn't working.

---

# 6. Example: Nginx → Express problem

Suppose your architecture is:

```text
Browser
   ↓
Nginx :80
   ↓
Express :5000
```

You visit:

```text
https://example.com/api/users
```

but receive:

```text
502 Bad Gateway
```

Instead of randomly changing your code, inspect:

```bash
sudo tail -f /var/log/nginx/error.log
```

You might discover that Nginx cannot connect to:

```text
127.0.0.1:5000
```

That immediately points you toward the Express process/port.

---

# 7. Application logs

Your Express application's logs are a separate matter.

If you run:

```bash
node server.js
```

and your application contains:

```javascript
console.log("Server started");
```

the output goes to the process's standard output.

For example:

```text
Server started
GET /api/users
POST /api/login
```

If you're running Node manually in SSH, you'll see these directly in your terminal.

But in production, you normally use a process manager/service and a deliberate logging strategy.

For example:

```text
systemd
   ↓
Node.js stdout/stderr
   ↓
journalctl
```

or a process manager/container may manage logs differently.

We'll get to this in the later **systemd/services** section.

---

# 8. `journalctl`

Modern Linux systems commonly use **systemd's journal** for system/service logs.

You can inspect it using:

```bash
journalctl
```

For example:

```bash
sudo journalctl -u nginx
```

This asks:

> Show me logs for the Nginx systemd service.

You can also follow new logs:

```bash
sudo journalctl -u nginx -f
```

This is similar in spirit to:

```bash
tail -f
```

but you're querying the systemd journal rather than a plain log file.

---

# 9. Why don't all logs have to be files?

Modern Linux systems don't necessarily put every log into a traditional text file.

A service can write to the **systemd journal**.

So you should understand both:

```text
Traditional/file-based logs
        ↓
/var/log/
```

and:

```text
systemd journal
        ↓
journalctl
```

Don't memorize:

> "Every Linux log is inside `/var/log`."

That's not correct.

---

# 10. Real production debugging

Imagine your deployed architecture:

```text
                    Internet
                       ↓
                     Nginx
                       ↓
                    Express
                       ↓
                    MongoDB
```

A user says:

> "The website isn't working."

You shouldn't immediately assume the Express code is broken.

You investigate layer by layer.

### Nginx:

```bash
sudo tail -f /var/log/nginx/error.log
```

### Nginx requests:

```bash
sudo tail -f /var/log/nginx/access.log
```

### Service logs:

```bash
sudo journalctl -u your-service
```

### Application:

Check Node/application logs.

### System:

```bash
sudo journalctl
```

This is the beginning of **production debugging**.

---

# 11. Useful commands

### List log files

```bash
ls /var/log
```

### Read a file

```bash
less /var/log/syslog
```

### Last few lines

```bash
tail /var/log/syslog
```

### Follow logs

```bash
tail -f /var/log/syslog
```

### Search logs

```bash
grep "error" /var/log/syslog
```

### systemd service logs

```bash
sudo journalctl -u nginx
```

### Follow systemd logs

```bash
sudo journalctl -u nginx -f
```

---

# 🧠 Interview Answer

If asked:

> **"Where are Linux logs stored?"**

A good answer is:

> **"Traditional Linux log files are commonly stored under `/var/log`, although modern systems using systemd also maintain logs in the systemd journal, which can be queried using `journalctl`. Services such as Nginx may have their own access and error logs."**

If asked:

> **"How would you debug Nginx?"**

Say:

```bash
sudo tail -f /var/log/nginx/error.log
```

and:

```bash
sudo tail -f /var/log/nginx/access.log
```

Then check the backend/service logs if Nginx is proxying to Express.
