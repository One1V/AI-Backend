
# Q74 — How do `journalctl` and system logs work?

This is a direct continuation of Q73.

The important thing to understand is:

> **`journalctl` is a command used to read logs collected by `systemd-journald`.**

This becomes especially important when you run your Node.js application as a **systemd service**.

---

# 1. What is `systemd`?

You've already seen this in your Linux roadmap.

`systemd` is the system and service manager used by many Linux distributions, including Ubuntu.

It manages things like:

```text
Nginx
SSH
Docker
Your Node.js application
```

Conceptually:

```text
Linux
  │
  ▼
systemd
  │
  ├── nginx.service
  ├── ssh.service
  ├── docker.service
  └── myapp.service
```

---

# 2. What is `journald`?

`systemd-journald` is a system service that **collects log messages** from the system and services.

Think of it as:

```text
Applications / Services
        │
        ▼
systemd-journald
        │
        ▼
Journal
        │
        ▼
journalctl
        │
        ▼
You
```

So:

```text
journald = collects logs

journalctl = lets you read/search them
```

---

# 3. Basic `journalctl`

Run:

```bash
journalctl
```

This can show journal entries from the system.

There can be a **lot** of output.

You can usually press:

```text
q
```

to exit the pager.

---

# 4. Logs for a specific service

This is where it becomes very useful.

Suppose Nginx is managed by systemd.

Run:

```bash
sudo journalctl -u nginx
```

`-u` means:

> Filter by systemd **unit**.

So:

```text
journalctl -u nginx
              ↑
             unit
```

You are asking:

> "Show me logs associated with the Nginx systemd service."

---

# 5. Follow logs in real time

Similar to:

```bash
tail -f
```

you can use:

```bash
sudo journalctl -u nginx -f
```

The `-f` means:

> Follow new log entries as they arrive.

So:

```text
Nginx
 ↓
produces log
 ↓
journald
 ↓
journalctl -f
 ↓
you see it immediately
```

This is extremely useful when debugging a live server.

---

# 6. Your Node.js application

This is where this becomes directly relevant to your deployment project.

Suppose eventually you create:

```text
/etc/systemd/system/myapp.service
```

and it runs:

```text
node /home/ubuntu/myapp/server.js
```

Your application contains:

```javascript
console.log("Server started");
```

and perhaps:

```javascript
console.error("Database connection failed");
```

When your Node application runs under systemd, its standard output/error can be collected by the journal.

Then you can use:

```bash
sudo journalctl -u myapp
```

to inspect the application's logs.

---

# 7. This is much better than SSH-only logging

Suppose you run your application manually:

```bash
node server.js
```

You see:

```text
Server started
Database connected
```

in your SSH terminal.

But that's not a proper production management strategy.

Instead:

```text
systemd
   ↓
Node.js
   ↓
stdout/stderr
   ↓
journald
   ↓
journalctl
```

Now logs can be inspected independently of the terminal session.

---

# 8. Useful filters

### Logs since today

```bash
sudo journalctl -u nginx --since today
```

### Logs from the last hour

```bash
sudo journalctl -u nginx --since "1 hour ago"
```

### Most recent entries

```bash
sudo journalctl -u nginx -n 50
```

This means:

> Show the last 50 entries.

### Follow live logs

```bash
sudo journalctl -u nginx -f
```

---

# 9. Kernel/system logs

You can also inspect broader system information:

```bash
journalctl -k
```

`-k` filters for kernel messages.

For example:

```text
Hardware
   ↓
Kernel
   ↓
journald
   ↓
journalctl -k
```

This can help when investigating system-level issues.

---

# 10. Priority filtering

You can also filter by severity.

For example:

```bash
sudo journalctl -p err
```

This asks for error-level messages and more severe entries.

Common priorities include:

```text
emerg
alert
crit
err
warning
notice
info
debug
```

You don't need to memorize all of them for a backend interview.

Knowing that logs can be filtered by **severity** is enough initially.

---

# 11. Example: Your Node server crashes

Suppose your production architecture is:

```text
Browser
   ↓
Nginx
   ↓
Node.js
   ↓
MongoDB
```

Suddenly users get:

```text
502 Bad Gateway
```

You check Nginx:

```bash
sudo journalctl -u nginx -n 50
```

Then your application:

```bash
sudo journalctl -u myapp -n 50
```

You might find:

```text
MongoServerSelectionError
```

Now you know the problem is likely in:

```text
Node.js → MongoDB
```

rather than:

```text
Browser → Nginx
```

That's the value of centralized service logs.

---

# 12. `journalctl` vs `/var/log`

This distinction is important.

### Traditional log files

```text
/var/log/
```

You might use:

```bash
tail -f /var/log/nginx/error.log
```

### systemd journal

```text
journald
```

You use:

```bash
journalctl -u nginx
```

They aren't necessarily competing systems.

A Linux service can have traditional log files, journal entries, or both depending on its configuration.

---

# 13. Important mental model

Don't think:

```text
journalctl = log file
```

Instead:

```text
systemd-journald
       ↓
collects log records
       ↓
journal
       ↓
journalctl
       ↓
query/filter/display
```

`journalctl` is essentially your **interface for querying the systemd journal**.

---

# 🧠 Interview Answer

If asked:

> **"What is journalctl?"**

Say:

> **"`journalctl` is the command-line utility used to query and inspect logs collected by `systemd-journald`. It can filter logs by service, time, priority, boot, and other criteria."**

If asked:

> **"How would you check logs for a Node.js systemd service called `myapp`?"**

Answer:

```bash
sudo journalctl -u myapp
```

For live logs:

```bash
sudo journalctl -u myapp -f
```

For the latest 50:

```bash
sudo journalctl -u myapp -n 50
```
