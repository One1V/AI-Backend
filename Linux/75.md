
# Q75 — How do you monitor Express logs?

When your Express application runs locally, you can simply see:

```bash
node server.js
```

and watch:

```text
Server started
GET /api/users
POST /api/login
Database connected
```

But in **production on your Linux VPS**, you need a proper way to monitor those logs.

---

# 1. First: `console.log()` is a log

Suppose your Express server has:

```javascript
app.get("/api/users", (req, res) => {
    console.log("GET /api/users");

    res.json({
        message: "Users fetched"
    });
});
```

When someone requests:

```text
GET /api/users
```

Node prints:

```text
GET /api/users
```

to its **standard output (stdout)**.

Similarly:

```javascript
console.error("Database connection failed");
```

writes to **stderr**.

Conceptually:

```text
Express
   │
   ├── console.log()
   │       ↓
   │      stdout
   │
   └── console.error()
           ↓
          stderr
```

---

# 2. Local development

If you run:

```bash
node server.js
```

you see the logs directly:

```text
Server running on port 5000
GET /api/users
POST /api/login
```

This is fine for development.

But imagine your VPS is running your application continuously.

You don't want to keep an SSH terminal open forever just to see:

```text
GET /api/users
```

That's where process/service management comes in.

---

# 3. Production: Express + systemd

Later in your Linux series, you'll learn how to create:

```text
/etc/systemd/system/myapp.service
```

which runs:

```text
Node.js
   ↓
Express
```

Your application might contain:

```javascript
console.log("Server started");

console.error("Something went wrong");
```

systemd can capture the process's output, and you can inspect it with:

```bash
sudo journalctl -u myapp
```

So the flow becomes:

```text
Express
   ↓
console.log()
   ↓
stdout
   ↓
systemd
   ↓
journald
   ↓
journalctl
```

---

# 4. Monitor logs live

This is probably the most useful command:

```bash
sudo journalctl -u myapp -f
```

`-f` means **follow**.

Now imagine you have:

```javascript
app.get("/api/users", (req, res) => {
    console.log("Users endpoint called");
    res.json({ users: [] });
});
```

You run:

```bash
sudo journalctl -u myapp -f
```

Then someone opens:

```text
https://example.com/api/users
```

You might see:

```text
Users endpoint called
```

immediately.

---

# 5. But Express logging can be better

You don't want to manually write:

```javascript
console.log(req.method, req.url);
```

inside every route.

That's why middleware such as **Morgan** is commonly used for HTTP request logging.

You already encountered Morgan in your Express learning.

Install it:

```bash
npm install morgan
```

Then:

```javascript
const morgan = require("morgan");

app.use(morgan("combined"));
```

Now requests can automatically produce logs such as:

```text
GET /api/users 200
POST /api/login 201
GET /api/products 404
```

The exact format depends on the Morgan format you select.

---

# 6. Why Morgan is useful

Without Morgan:

```text
Request
   ↓
Express
   ↓
Your route
   ↓
Maybe console.log()
```

With Morgan:

```text
Request
   ↓
Morgan middleware
   ↓
Express
   ↓
Route
```

Morgan can automatically log useful HTTP information.

For example:

```text
GET /api/users
POST /api/login
404 /api/random
500 /api/payment
```

This is extremely useful when debugging production APIs.

---

# 7. Example production architecture

Your eventual architecture can look like:

```text
                    Internet
                       │
                       ▼
                    Nginx
                       │
                       ▼
                  Express
                       │
                 Morgan/logging
                       │
                       ▼
                  stdout/stderr
                       │
                       ▼
                   systemd
                       │
                       ▼
                  journald
                       │
                       ▼
                 journalctl
```

You can then inspect:

```bash
sudo journalctl -u myapp -f
```

---

# 8. Example: debugging a 500 error

Suppose a user says:

> "Whenever I click Login, I get an error."

The request is:

```text
POST /api/login
```

Morgan might show:

```text
POST /api/login 500
```

Then your application logs might show:

```text
Database connection timeout
```

Now you know:

```text
Browser
   ↓
Nginx                 ✅
   ↓
Express               ✅
   ↓
Login route            ✅
   ↓
Database connection    ❌
```

That's much better than randomly changing your frontend code.

---

# 9. Nginx logs vs Express logs

This distinction is important.

### Nginx

```text
/var/log/nginx/access.log
/var/log/nginx/error.log
```

Nginx is concerned with:

```text
HTTP requests
reverse proxying
connections
TLS/HTTPS
upstream failures
```

### Express

Your application logs are concerned with:

```text
routes
authentication
database operations
business logic
application errors
```

So:

```text
Browser
   ↓
Nginx
   │
   └── Nginx logs
   ↓
Express
   │
   └── Application logs
   ↓
MongoDB
```

Each layer has its own useful logs.

---

# 10. Don't log sensitive information

This is extremely important.

❌ Don't do:

```javascript
console.log(req.body);
```

if the body contains:

```text
password
credit card information
JWT
API keys
```

Also avoid:

```javascript
console.log(process.env.JWT_SECRET);
```

Your logs themselves can become a security problem.

A good production logging strategy should avoid exposing sensitive data.

---

# 11. What should you log?

Useful examples:

```text
Request method
URL/route
Status code
Response time
User/request ID
Error information
Important application events
```

For example:

```text
POST /api/login 401 32ms
```

is useful.

But:

```text
POST /api/login password=MyPassword123
```

is dangerous.

---

# 12. Logs aren't just for errors

A common beginner misconception is:

> "Logs are only for errors."

No.

Logs help you understand **what the application is doing**.

For example:

```text
Server started
Database connected
POST /api/login 200
GET /api/profile 200
POST /api/payment 500
```

You can reconstruct what happened.

---

# 🧠 Interview Answer

If asked:

> **"How do you monitor an Express application in production?"**

A strong answer:

> **"At the application level, I can use structured/application logging and HTTP logging middleware such as Morgan. If the application runs as a systemd service, its stdout and stderr can be collected by the systemd journal, which I can monitor using `journalctl -u myapp -f`. I would also monitor Nginx logs separately because Nginx and Express operate at different layers."**

---

# 🔑 Remember

```text
Express
   ↓
Morgan / application logging
   ↓
stdout / stderr
   ↓
systemd
   ↓
journald
   ↓
journalctl
```

Useful command:

```bash
sudo journalctl -u myapp -f
```

And for Nginx:

```bash
sudo tail -f /var/log/nginx/access.log
```

```bash
sudo tail -f /var/log/nginx/error.log
```
