
# Q76 — How do you monitor Nginx logs?

Since you've already built:

```text
Browser
   ↓
Nginx :80
   ↓
Express :5000
```

this question is **very practical for you**.

Nginx generally gives you two important logs:

```text
access.log
error.log
```

---

# 1. Where are Nginx logs?

On Ubuntu, commonly:

```text
/var/log/nginx/
```

Check:

```bash
ls /var/log/nginx
```

You'll typically see:

```text
access.log
error.log
```

---

# 2. `access.log`

`access.log` records requests that Nginx processes.

For example, a user visits:

```text
https://example.com/
```

Nginx may record something conceptually like:

```text
GET / 200
```

If they request:

```text
/api/users
```

you might see:

```text
GET /api/users 200
```

So:

```text
Browser
   ↓
Request
   ↓
Nginx
   ↓
access.log
```

---

# 3. Watch access logs live

Use:

```bash
sudo tail -f /var/log/nginx/access.log
```

Now keep this terminal open.

Then visit your website from your browser.

You should see new requests appearing.

For example:

```text
GET / 200
GET /style.css 200
GET /api/users 200
```

This is one of the simplest ways to verify:

> **Is the request actually reaching Nginx?**

---

# 4. `error.log`

The other important file is:

```text
/var/log/nginx/error.log
```

It contains Nginx errors and diagnostic information.

Monitor it:

```bash
sudo tail -f /var/log/nginx/error.log
```

This becomes particularly useful for errors such as:

```text
502 Bad Gateway
403 Forbidden
404 Not Found
500 Internal Server Error
permission denied
upstream connection failures
```

---

# 5. Real example: 502 Bad Gateway

Your architecture:

```text
Browser
   ↓
Nginx :80
   ↓
Express :5000
```

Suppose your Express server crashes.

Now the browser requests:

```text
GET /api/users
```

Nginx tries:

```text
127.0.0.1:5000
```

but nothing is listening there.

You may get:

```text
502 Bad Gateway
```

Check:

```bash
sudo tail -f /var/log/nginx/error.log
```

You may see an upstream connection error.

That tells you:

```text
Browser → Nginx       ✅
Nginx → Express       ❌
```

So you should investigate the Node process.

---

# 6. Real example: permission denied

You previously encountered a similar Nginx problem.

Suppose Nginx needs:

```text
/home/ayush/project/public/index.html
```

but Linux permissions prevent Nginx from reading it.

The browser may receive:

```text
403 Forbidden
```

Check:

```bash
sudo tail -f /var/log/nginx/error.log
```

You could find something indicating:

```text
permission denied
```

Now you know:

```text
Browser
   ↓
Nginx                 ✅
   ↓
Linux file permission ❌
```

This is exactly where your **Linux permissions knowledge** becomes useful.

---

# 7. Access vs Error log

Remember this simple distinction:

### `access.log`

> **What requests came in?**

```text
GET /
POST /api/login
GET /api/users
```

### `error.log`

> **What went wrong with Nginx?**

```text
permission denied
connection refused
upstream failure
configuration problem
```

---

# 8. Useful commands

### See recent access logs

```bash
sudo tail /var/log/nginx/access.log
```

### Follow access logs

```bash
sudo tail -f /var/log/nginx/access.log
```

### See recent errors

```bash
sudo tail /var/log/nginx/error.log
```

### Follow errors

```bash
sudo tail -f /var/log/nginx/error.log
```

### Search for errors

```bash
sudo grep "error" /var/log/nginx/error.log
```

---

# 9. Combine with your Express logs

This is where production debugging becomes powerful.

Suppose:

```text
Browser
   ↓
Nginx
   ↓
Express
   ↓
MongoDB
```

You can monitor each layer:

### Nginx access

```bash
sudo tail -f /var/log/nginx/access.log
```

### Nginx errors

```bash
sudo tail -f /var/log/nginx/error.log
```

### Express/systemd

```bash
sudo journalctl -u myapp -f
```

Then you can determine **where the request failed**.

---

# 10. Example debugging session

User reports:

> "The API isn't working."

You send:

```bash
curl http://your-domain.com/api/users
```

You get:

```text
502 Bad Gateway
```

### Step 1 — Nginx access log

```bash
sudo tail /var/log/nginx/access.log
```

You see:

```text
GET /api/users 502
```

Therefore:

```text
Request reached Nginx ✅
```

### Step 2 — Nginx error log

```bash
sudo tail /var/log/nginx/error.log
```

You see an upstream connection error.

Therefore:

```text
Nginx → Express ❌
```

### Step 3 — Check Express

```bash
sudo journalctl -u myapp -n 50
```

Maybe you discover:

```text
Application crashed
```

Now you've located the problem.

---

# 11. Why logs are so important in production

You can't rely on:

```text
"Let me open the code and see."
```

A production server might have:

```text
10,000 requests
100 errors
3 failed logins
2 crashed processes
```

Logs give you evidence of what happened.

This is why a backend engineer should be comfortable with:

```text
grep
tail
journalctl
Nginx logs
application logs
```

---

# 🧠 Interview Answer

If asked:

> **"How do you monitor Nginx logs?"**

Say:

> **"On Ubuntu, Nginx commonly stores access and error logs under `/var/log/nginx/`. I can use `tail -f /var/log/nginx/access.log` to monitor incoming requests and `tail -f /var/log/nginx/error.log` to investigate Nginx errors such as permission issues or upstream connection failures."**

If they ask:

> **"How would you debug a 502 from Nginx?"**

A strong answer:

```text
Check Nginx error.log
        ↓
Check whether Express is running
        ↓
Check whether port 5000 is listening
        ↓
Check Express/service logs
        ↓
Fix the underlying issue
```

Commands:

```bash
sudo tail -f /var/log/nginx/error.log
```

then:

```bash
sudo ss -ltnp | grep :5000
```

and:

```bash
sudo journalctl -u myapp -n 50
```
