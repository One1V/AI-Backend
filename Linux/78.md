
# Q78 — How do you identify high memory usage in Linux?

This is similar to Q77, but now we're investigating **RAM**, not CPU.

Imagine your VPS has:

```text
RAM = 2 GB
```

and your Express application suddenly becomes slow or crashes.

You need to determine:

> **Is the server running out of memory?**

---

# 1. First tool: `free`

Run:

```bash
free -h
```

Example:

```text
               total   used   free   shared   buff/cache   available
Mem:            2.0Gi   1.5Gi  100Mi   50Mi     400Mi        350Mi
Swap:           1.0Gi   200Mi  800Mi
```

The `-h` means **human-readable**.

So instead of:

```text
2097152
```

you get:

```text
2.0Gi
```

---

# 2. The most important column: `available`

Beginners often look only at:

```text
free
```

But Linux uses otherwise-unused RAM for things such as filesystem caches.

So when assessing whether the system is under memory pressure, **`available` is generally more useful than `free`**.

For example:

```text
free:       100 MB
available:  350 MB
```

doesn't necessarily mean only 100 MB can be used.

Linux can reclaim some cached memory.

---

# 3. Check memory with `top`

Run:

```bash
top
```

At the top you'll see memory information.

You can also look at the process list:

```text
PID    USER     %CPU   %MEM   COMMAND
1234   ubuntu    5.0   35.0   node
2311   mongodb   2.0   25.0   mongod
```

Here:

```text
node → 35% RAM
```

could be significant depending on the total memory available.

---

# 4. `htop`

Run:

```bash
htop
```

You'll get a visual representation of:

```text
CPU
Memory
Swap
```

and the processes underneath.

For example:

```text
Mem [||||||||||||||||    ] 75%
Swp [||||                ] 10%

PID    CPU%    MEM%    COMMAND
1234   5.0     35.0    node server.js
2311   2.0     25.0    mongod
```

It's a convenient way to identify memory-heavy processes.

---

# 5. Find the biggest memory-consuming processes

Use:

```bash
ps aux --sort=-%mem
```

This sorts processes by memory usage.

You might see:

```text
USER      PID    %CPU   %MEM   COMMAND
ubuntu    1234    5.0   35.0   node server.js
mongodb   2311    2.0   25.0   mongod
root      1522    1.0   10.0   nginx
```

To show only the top few:

```bash
ps aux --sort=-%mem | head
```

Now you can quickly identify the largest consumers.

---

# 6. What is swap?

Suppose your VPS has:

```text
RAM = 2 GB
```

but applications need more memory.

Linux may use **swap**, which is disk space used as an extension of memory.

Conceptually:

```text
RAM
 ↓
Full
 ↓
Some memory pages
 ↓
Swap on disk
```

You can check it using:

```bash
free -h
```

Example:

```text
Swap:
total   1.0Gi
used    800Mi
free    200Mi
```

Heavy swap usage can indicate **memory pressure** and may make the system much slower because disk storage is far slower than RAM.

---

# 7. Why might a Node.js application use too much memory?

This is where backend knowledge comes in.

For example, imagine:

```javascript
const cache = [];

setInterval(() => {
    cache.push(new Array(100000).fill("data"));
}, 1000);
```

The application keeps allocating memory without releasing it.

Conceptually:

```text
Node
 ↓
Memory allocation
 ↓
Memory allocation
 ↓
Memory allocation
 ↓
RAM usage ↑
 ↓
Server memory pressure
```

This could be a sign of a memory leak or simply an unbounded data structure.

---

# 8. Another common mistake

Suppose your API does:

```javascript
const users = await User.find({});
```

and your database contains:

```text
5 million users
```

You might accidentally load a huge dataset into application memory.

Instead, production applications commonly use techniques such as:

```text
pagination
projection/select
streaming where appropriate
efficient queries
```

The Linux tools tell you:

> **"Memory is high."**

Your application/database investigation tells you:

> **"Why?"**

---

# 9. Node.js-specific memory

You can inspect Node's memory from inside your application:

```javascript
console.log(process.memoryUsage());
```

You might see values such as:

```text
rss
heapTotal
heapUsed
external
arrayBuffers
```

For example:

```javascript
console.log(process.memoryUsage().heapUsed);
```

This helps you investigate Node's own memory usage.

So you have two levels:

```text
Linux
 ↓
Is the server running out of RAM?

Node.js
 ↓
Why is my application using so much memory?
```

---

# 10. Real production example

Suppose your VPS has:

```text
2 GB RAM
```

Users complain:

> "The API is extremely slow."

You SSH in:

```bash
ssh ubuntu@SERVER_IP
```

First:

```bash
free -h
```

You discover:

```text
available: 100 MB
swap: heavily used
```

That's a warning sign.

Then:

```bash
ps aux --sort=-%mem | head
```

You discover:

```text
node     35%
mongod   40%
```

Then inspect the application:

```bash
sudo journalctl -u myapp -n 100
```

and investigate Node's memory behavior.

# 11. CPU vs Memory

This is an important distinction from the previous question.

### Q77 — CPU

```text
top
htop
ps aux --sort=-%cpu
```

Question:

> **Which process is using too much CPU?**

### Q78 — Memory

```text
free -h
top
htop
ps aux --sort=-%mem
```

Question:

> **Which process is using too much RAM?**

# 12. What happens if memory is exhausted?

If the system runs out of usable memory, Linux may invoke the **OOM (Out Of Memory) killer** to terminate processes and recover memory.

You might see evidence of this in system logs.

For example:

```bash
journalctl -k
```

or:

```bash
dmesg
```

may help investigate kernel messages, depending on permissions and system configuration.

Conceptually:

```text
RAM exhausted
     ↓
Memory allocation fails / severe pressure
     ↓
Linux may invoke OOM killer
     ↓
A process may be terminated
```

This is one reason memory monitoring matters in production.

# 🧠 Interview Answer

If asked:

> **"How do you identify high memory usage on Linux?"**

Say:

> **"I'd first use `free -h` to check overall memory and swap usage, then use `top` or `htop` to identify memory-heavy processes. I can also use `ps aux --sort=-%mem` to rank processes by memory consumption. If my Node.js process is using excessive memory, I'd investigate its heap usage and application behavior."**

Useful commands:

```bash
free -h
```

```bash
htop
```

```bash
ps aux --sort=-%mem
```
