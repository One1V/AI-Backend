
# Q80 — Mini Project: Debug a Production Server

This is the **capstone of Module 9 — Logs & Monitoring**.

You are given a realistic production problem:

> **Users report that your backend is slow and sometimes returns errors.**

Your server looks like:

```text
                    Internet
                       │
                       ▼
                    Nginx
                    :80/443
                       │
                       ▼
                  Express/Node
                    :5000
                       │
                       ▼
                   MongoDB
```

Your job is to **find the problem instead of guessing**.

---

# 🎯 Scenario

You have an Ubuntu VPS running:

```text
Nginx
Express
MongoDB
```

Users report:

```text
❌ Website is slow
❌ Some API requests return 502
❌ Deployment recently failed
```

You SSH into the server:

```bash
ssh ubuntu@SERVER_IP
```

Now start debugging.

---

# Step 1 — Check if the server is alive

Run:

```bash
uptime
```

Example:

```text
load average: 8.5, 7.9, 6.2
```

This tells you the system has significant load.

But don't conclude immediately that CPU is the problem.

---

# Step 2 — Check CPU

Run:

```bash
top
```

or:

```bash
htop
```

Suppose you discover:

```text
PID     %CPU     COMMAND
1234    95%      node server.js
```

Your Node process is consuming a lot of CPU.

You can confirm:

```bash
ps aux --sort=-%cpu | head
```

You now know:

```text
Node.js → very high CPU
```

But **don't immediately kill it**.

You need to determine why.

---

# Step 3 — Check memory

Run:

```bash
free -h
```

Suppose:

```text
Mem:
total       2.0Gi
used        1.9Gi
available   100Mi

Swap:
total       1.0Gi
used        900Mi
```

That's serious memory pressure.

Now:

```bash
ps aux --sort=-%mem | head
```

You discover:

```text
node      40%
mongod    35%
```

So you now have:

```text
CPU → High
Memory → Very high
```

---

# Step 4 — Check disk

Run:

```bash
df -h
```

Suppose:

```text
Filesystem      Size   Used   Avail   Use%
/dev/sda1       40G    39G    1G      98%
```

That's another problem.

Now investigate:

```bash
sudo du -sh /var/*
```

You find:

```text
8G     /var/log
15G    /var/lib/docker
```

Now you know your server is also almost out of disk space.

---

# Step 5 — Check Nginx

Now investigate the reverse proxy.

### Access log

```bash
sudo tail -f /var/log/nginx/access.log
```

You might see:

```text
GET /api/users 200
GET /api/products 200
GET /api/orders 502
GET /api/orders 502
```

So Nginx is receiving requests.

---

# Step 6 — Check Nginx errors

Run:

```bash
sudo tail -f /var/log/nginx/error.log
```

Suppose you see an upstream connection error.

That suggests:

```text
Browser
   ↓
Nginx                ✅
   ↓
Express :5000        ❌/unstable
```

Now investigate Express.

---

# Step 7 — Check the Express service

Suppose you run Node through systemd:

```text
myapp.service
```

Check:

```bash
sudo systemctl status myapp
```

Maybe you see:

```text
Active: failed
```

That's a major clue.

Now inspect the logs:

```bash
sudo journalctl -u myapp -n 100
```

You might find:

```text
JavaScript heap out of memory
```

or:

```text
Database connection timeout
```

or:

```text
Application crashed
```

Now you're getting close to the root cause.

---

# Step 8 — Check whether port 5000 is listening

Run:

```bash
sudo ss -ltnp | grep :5000
```

If nothing appears:

```text
Nginx
   ↓
127.0.0.1:5000
   ↓
❌ Nothing listening
```

That explains the 502.

If you see:

```text
LISTEN
127.0.0.1:5000
node
```

then Node is listening, and you need to investigate further.

---

# Step 9 — Test Express directly

This is a very useful debugging technique.

Instead of going through Nginx:

```text
Browser → Nginx → Express
```

test Express directly:

```bash
curl http://127.0.0.1:5000/api/users
```

### If it works:

```text
curl → Express → 200
```

but:

```text
Browser → Nginx → 502
```

then Nginx configuration/networking becomes suspicious.

### If it fails:

```text
curl → Express → ❌
```

then the problem is probably within the application/service.

This is called **isolating layers**.

---

# Step 10 — Build the complete diagnosis

Suppose your investigation found:

```text
CPU             → 95%
Memory          → almost full
Disk            → 98% full
Nginx           → 502 errors
Node            → unstable
Logs            → huge
```

Don't treat these as five unrelated problems.

There may be a chain:

```text
Application problem
       ↓
Node generates excessive logs
       ↓
Logs consume disk
       ↓
Disk becomes almost full
       ↓
Application/Nginx operations fail
       ↓
Requests return errors
```

Or there could be multiple independent issues.

**Your job is to establish the causal chain from evidence.**

# 🧠 Production Debugging Checklist

When a production server is behaving badly:

### 1. System health

```bash
uptime
```

### 2. CPU

```bash
top
```

```bash
ps aux --sort=-%cpu | head
```

### 3. Memory

```bash
free -h
```

```bash
ps aux --sort=-%mem | head
```

### 4. Disk

```bash
df -h
```

```bash
sudo du -sh /var/*
```

### 5. Nginx

```bash
sudo tail -f /var/log/nginx/error.log
```

### 6. Application

```bash
sudo systemctl status myapp
```

```bash
sudo journalctl -u myapp -n 100
```

### 7. Port

```bash
sudo ss -ltnp | grep :5000
```

### 8. Direct application test

```bash
curl http://127.0.0.1:5000
```

# 🔥 The Most Important Concept

Don't memorize commands independently.

Think in **layers**:

```text
                  USER REPORT
                      │
                      ▼
              Is server alive?
                      │
                      ▼
              CPU / Memory / Disk
                      │
                      ▼
                   Nginx
                      │
                      ▼
                  Port 5000
                      │
                      ▼
                  Express
                      │
                      ▼
                  MongoDB
```

At each layer, ask:

> **"Is this layer working?"**

This is much more valuable than memorizing 50 Linux commands.

---

# 🎯 Interview Question

If an interviewer says:

> **"Your Node.js backend is returning 502 errors in production. How would you debug it?"**

Don't say:

> "I'll restart the server."

Give a structured answer:

> **"First I'd check Nginx's error logs to understand whether the 502 is caused by an upstream failure. Then I'd verify that the Node.js process is running and that port 5000 is listening using `systemctl` and `ss`. I'd test the Express application directly with `curl` to isolate Nginx from the application. I'd also check the application's systemd logs with `journalctl`, and inspect CPU, memory, and disk usage in case resource exhaustion is causing the failure."**

That's a **strong backend/Linux interview answer**.
