
# Q81 — What is `systemd`?

`systemd` is one of the **most important Linux concepts for backend deployment**.

You have already seen the problem:

```text
SSH
 ↓
node server.js
 ↓
Express running
 ↓
SSH closes
 ↓
Node stops
```

`systemd` helps solve this by managing your application as a **Linux service**.

---

# 1. What is systemd?

Simply:

> **systemd is the system and service manager used by many modern Linux distributions.**

It can:

* start services
* stop services
* restart services
* monitor services
* start services automatically when the server boots
* manage service logs
* manage dependencies between services

Think of it as a **manager for long-running processes**.

---

# 2. Real example: your Express backend

Suppose your backend is:

```text
/home/ayush/myapp/server.js
```

Normally:

```bash
node server.js
```

starts your application.

But if you close SSH, your process may terminate depending on how you started it.

With `systemd`:

```text
Linux
  ↓
systemd
  ↓
myapp.service
  ↓
Node.js
  ↓
Express
```

Now Linux treats your backend as a managed service.

---

# 3. What is a service?

A **service** is generally a long-running background program managed by the operating system.

Examples:

```text
nginx.service
ssh.service
docker.service
mongodb.service
```

Your Node application can also become:

```text
myapp.service
```

So instead of manually doing:

```bash
node server.js
```

you can do:

```bash
sudo systemctl start myapp
```

---

# 4. Where does systemd get its instructions?

You create a **service unit file**.

For example:

```text
/etc/systemd/system/myapp.service
```

A simplified example:

```ini
[Unit]
Description=My Express Backend
After=network.target

[Service]
User=ayush
WorkingDirectory=/home/ayush/myapp
ExecStart=/usr/bin/node server.js
Restart=always

[Install]
WantedBy=multi-user.target
```

Don't worry about memorizing every line yet.

You'll learn service files properly in the next questions.

---

# 5. What happens when you start it?

You run:

```bash
sudo systemctl start myapp
```

Conceptually:

```text
You
 ↓
systemctl
 ↓
systemd
 ↓
myapp.service
 ↓
Node.js
 ↓
Express
```

Your Express server is now running under systemd's management.

---

# 6. Check whether it's running

Use:

```bash
sudo systemctl status myapp
```

You might see:

```text
● myapp.service
     Loaded: loaded
     Active: active (running)
     Main PID: 1234
     CGroup: /system.slice/myapp.service
             └─1234 /usr/bin/node server.js
```

The important part:

```text
Active: active (running)
```

means your service is currently running.

---

# 7. Stop the application

Instead of:

```bash
kill ...
```

you can use:

```bash
sudo systemctl stop myapp
```

Flow:

```text
systemctl stop
      ↓
    systemd
      ↓
   Node stops
```

---

# 8. Restart the application

After deploying a change:

```bash
sudo systemctl restart myapp
```

For example:

```text
Git pull
   ↓
Code updated
   ↓
Restart service
   ↓
New Node process
   ↓
New code running
```

---

# 9. The BIG advantage: automatic restart

Suppose your Node application crashes:

```text
Node.js
   ↓
CRASH ❌
```

If your service contains:

```ini
Restart=always
```

systemd can restart it.

Conceptually:

```text
Node
 ↓
Crash ❌
 ↓
systemd detects failure
 ↓
Restart
 ↓
Node starts again
```

This is a major reason service managers are useful in production.

---

# 10. Start automatically after reboot

Imagine your VPS restarts.

Without proper service configuration:

```text
VPS reboot
 ↓
Linux starts
 ↓
Node ❌
```

You'd have to SSH in and manually start it.

With:

```bash
sudo systemctl enable myapp
```

you configure the service to start automatically during boot.

Then:

```text
VPS reboot
     ↓
Linux boots
     ↓
systemd
     ↓
myapp.service
     ↓
Node.js
     ↓
Express
```

This is extremely useful for production.

---

# 11. `systemctl` vs `systemd`

This distinction is important.

### `systemd`

The actual **system/service manager**.

### `systemctl`

The **command-line tool used to communicate with systemd**.

Think:

```text
systemd
  ↑
systemctl
```

You use:

```bash
systemctl start
systemctl stop
systemctl restart
systemctl status
systemctl enable
```

to control systemd-managed services.

---

# 12. systemd vs PM2

You asked about PM2 earlier.

Both can manage Node.js applications.

### PM2

```text
Node.js
   ↑
 PM2
```

### systemd

```text
Node.js
   ↑
systemd
```

PM2 is specifically designed around Node.js process management.

`systemd` is the Linux operating system's general service manager.

For example, systemd can manage:

```text
Nginx
SSH
Docker
MongoDB
Node
```

not just Node applications.

# 🧠 Interview Answer

If asked:

> **"What is systemd?"**

A strong answer:

> **"systemd is the system and service manager used by modern Linux systems. It manages services and long-running processes, including starting, stopping, restarting, monitoring, and automatically starting services during boot. For example, I can run a Node.js Express backend as a systemd service and use `systemctl` to manage it."**

If they ask:

> **"What's the difference between systemd and systemctl?"**

Say:

> **"`systemd` is the service manager itself, while `systemctl` is the command-line interface used to control systemd-managed services."**
