# Q83 — How do `systemctl start`, `stop`, `restart`, and `status` work?

These are the **four `systemctl` commands you should absolutely know** for backend deployment.

Suppose your Express application is registered as:

```text
myapp.service
```

---

## 1. `systemctl start`

Starts the service **right now**.

```bash
sudo systemctl start myapp
```

Flow:

```text
systemctl start myapp
        ↓
      systemd
        ↓
   myapp.service
        ↓
    Node.js
        ↓
     Express
```

If your application was stopped:

```text
myapp → stopped ❌
```

after:

```bash
sudo systemctl start myapp
```

it becomes:

```text
myapp → running ✅
```

### Important

`start` does **not** mean:

> "Start this automatically every time the server boots."

It only starts it **now**.

Automatic startup is handled by `enable`.

---

# 2. `systemctl stop`

Stops the service.

```bash
sudo systemctl stop myapp
```

Flow:

```text
systemctl stop
      ↓
    systemd
      ↓
myapp.service
      ↓
 Node.js stops
```

Your Express API will no longer be available.

For example:

```text
Browser
   ↓
Nginx
   ↓
Express ❌
```

Nginx may then return:

```text
502 Bad Gateway
```

depending on the configuration and failure mode.

---

# 3. `systemctl restart`

This is extremely common during deployment.

```bash
sudo systemctl restart myapp
```

It essentially does:

```text
Stop old process
       ↓
Start new process
```

For example:

```text
Old Node.js
    ↓
   stop
    ↓
   start
    ↓
New Node.js
```

### Real deployment example

Suppose you push new code:

```bash
git pull origin main
```

Your server now has the updated code.

But the currently running Node process may still be using the old process state/code.

You can restart:

```bash
sudo systemctl restart myapp
```

Now the application starts again using the updated code.

---

# 4. `systemctl status`

This tells you the current state of the service.

```bash
sudo systemctl status myapp
```

You might see:

```text
● myapp.service
     Loaded: loaded
     Active: active (running)
   Main PID: 1234
```

The most important line is:

```text
Active: active (running)
```

That means the service is currently running.

---

# 5. Possible states

You might see:

### Running

```text
Active: active (running)
```

✅ Service is running.

### Stopped

```text
Active: inactive (dead)
```

The service isn't currently running.

### Failed

```text
Active: failed
```

Something went wrong while starting or running it.

This is when you should investigate the logs:

```bash
sudo journalctl -u myapp
```

---

# 6. Real debugging example

Suppose your website suddenly gives:

```text
502 Bad Gateway
```

You SSH into the server:

```bash
ssh ubuntu@SERVER_IP
```

Check:

```bash
sudo systemctl status myapp
```

You discover:

```text
Active: failed
```

Now check:

```bash
sudo journalctl -u myapp -n 50
```

Maybe:

```text
Error: Cannot connect to MongoDB
```

Now you have a much better idea of what caused the failure.

---

# 7. `start` vs `enable`

This is a **very common interview question**.

### `start`

```bash
sudo systemctl start myapp
```

Means:

> Start the service **now**.

### `enable`

```bash
sudo systemctl enable myapp
```

Means:

> Configure the service to start automatically during boot.

So:

```text
start
 ↓
NOW
```

while:

```text
enable
 ↓
FUTURE BOOTS
```

You can do both:

```bash
sudo systemctl enable --now myapp
```

This enables the service for boot **and** starts it immediately.

---

# 8. Typical production workflow

Suppose you deploy your Express backend.

### First deployment

```bash
sudo systemctl start myapp
```

Then:

```bash
sudo systemctl enable myapp
```

Now:

```text
Server running
      ↓
Reboot VPS
      ↓
systemd
      ↓
myapp automatically starts
```

---

# 9. After updating code

Typical flow:

```bash
git pull origin main
```

Then:

```bash
sudo systemctl restart myapp
```

Then verify:

```bash
sudo systemctl status myapp
```

Then inspect logs if needed:

```bash
sudo journalctl -u myapp -f
```

So:

```text
Git pull
   ↓
Updated code
   ↓
systemctl restart
   ↓
New Node process
   ↓
status
   ↓
logs
```

---

# 10. Don't confuse `restart` with `reload`

You'll sometimes encounter:

```bash
systemctl reload nginx
```

A **restart** generally stops and starts the service.

A **reload** asks a service to reload its configuration without fully stopping the running process, if that service supports reloads.

For example, after changing Nginx configuration:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

is often preferable to restarting Nginx.

For your Node application, whether reload is supported/useful depends on how the application is managed.

---

# 🧠 Interview Answer

If asked:

> **"Explain `systemctl start`, `stop`, `restart`, and `status`."**

Say:

> **"`start` starts a service immediately, `stop` stops it, `restart` stops and starts it again, and `status` shows its current state along with useful information such as the PID and recent service details."**

Then add:

> **"`enable` is different from `start`: `enable` configures the service to start automatically when Linux boots."**

That's a very solid answer.

---

# 🔑 Cheat Sheet

```bash
# Start now
sudo systemctl start myapp

# Stop now
sudo systemctl stop myapp

# Restart
sudo systemctl restart myapp

# Check status
sudo systemctl status myapp

# Start automatically after boot
sudo systemctl enable myapp

# Enable + start immediately
sudo systemctl enable --now myapp

# View logs
sudo journalctl -u myapp
```

```text
                    │

     start        stop        restart
       │            │            │

                    │
                    ↓
                 Node.js
                    ↓
                 Express
```
