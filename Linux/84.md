
# Q84 — How do you enable services at boot?

Suppose you have deployed your Express backend on a VPS:

```text
VPS
 ↓
Linux
 ↓
systemd
 ↓
myapp.service
 ↓
Node.js / Express
```

Everything works.

But then the VPS **reboots**.

Without configuring the service properly:

```text
VPS reboot
   ↓
Linux starts
   ↓
Node.js ❌
   ↓
Website/API down
```

You want Linux to automatically start your application.

That's what **`systemctl enable`** is for.

---

## 1. The basic command

```bash
sudo systemctl enable myapp
```

This tells systemd:

> **"Start `myapp.service` automatically during the appropriate boot target."**

It does **not necessarily start the service immediately**.

So:

```bash
systemctl enable myapp
```

means:

```text
Future boot → start automatically
```

---

# 2. `enable` vs `start`

This is extremely important.

### Start

```bash
sudo systemctl start myapp
```

Means:

> Start it **right now**.

### Enable

```bash
sudo systemctl enable myapp
```

Means:

> Start it **automatically when the system boots**.

Think:

```text
start
 ↓
NOW
```

```text
enable
 ↓
BOOT
```

---

# 3. Typical deployment

Suppose you've created:

```text
/etc/systemd/system/myapp.service
```

First tell systemd about the new service definition:

```bash
sudo systemctl daemon-reload
```

Then start it:

```bash
sudo systemctl start myapp
```

Then enable it:

```bash
sudo systemctl enable myapp
```

Now:

```text
Current server
     ↓
myapp running ✅

Server reboot
     ↓
Linux boots
     ↓
systemd
     ↓
myapp starts automatically ✅
```

---

# 4. Better: enable + start together

You can do both in one command:

```bash
sudo systemctl enable --now myapp
```

This means:

```text
enable → automatic startup
+
now → start immediately
```

So after running it:

```text
myapp
 ├── running now ✅
 └── enabled for future boots ✅
```

---

# 5. Verify it

Check whether the service is enabled:

```bash
systemctl is-enabled myapp
```

You should get:

```text
enabled
```

Then check whether it's currently running:

```bash
sudo systemctl status myapp
```

You might see:

```text
Active: active (running)
```

So there are actually **two different questions**:

### Is it running right now?

```bash
systemctl is-active myapp
```

### Will it start at boot?

```bash
systemctl is-enabled myapp
```

# 7. What happens after reboot?

Suppose you execute:

```bash
sudo reboot
```

The server shuts down and starts again.

Linux boots.

During boot, systemd reads its enabled services.

Because you previously ran:

```bash
sudo systemctl enable myapp
```

systemd knows:

> `myapp.service` should be started during boot.

So:

```text
VPS reboot
    ↓
Linux kernel
    ↓
systemd starts
    ↓
myapp.service starts
    ↓
Node.js starts
    ↓
Express listens on :5000
    ↓
Nginx can proxy requests
```

You don't have to SSH in and manually run:

```bash
node server.js
```

---

# 8. What if you only use `start`?

Suppose you do:

```bash
sudo systemctl start myapp
```

Everything works:

```text
myapp → running ✅
```

Then:

```bash
sudo reboot
```

After reboot:

```text
myapp → not automatically started ❌
```

because `start` doesn't configure boot-time startup.

This is a common beginner mistake.

---

# 9. What if you only use `enable`?

Suppose you do:

```bash
sudo systemctl enable myapp
```

The service is configured for future boots.

But it may **not start immediately**.

You can check:

```bash
systemctl is-active myapp
```

It could return:

```text
inactive
```

So if you want both:

```bash
sudo systemctl enable --now myapp
```

---

# 10. `disable`

The opposite of `enable` is:

```bash
sudo systemctl disable myapp
```

This means:

> Don't automatically start this service during future boots.

It doesn't necessarily stop a currently running service.

So:

```text
disable
 ↓
Remove automatic boot startup
```

If you also want to stop it now:

```bash
sudo systemctl disable --now myapp
```

---

# 🧠 Interview Answer

If asked:

> **"How do you configure a service to start automatically at boot?"**

Say:

> **"I use `systemctl enable <service>`. For example, `sudo systemctl enable myapp` configures my Node.js service to start automatically during boot. If I also want to start it immediately, I can use `sudo systemctl enable --now myapp`."**

If they ask:

> **"What's the difference between `enable` and `start`?"**

Answer:

> **"`start` starts the service immediately, while `enable` configures it to start automatically during future system boots."**

---

# 🔑 Remember

```bash
# Start now
sudo systemctl start myapp

# Start automatically at boot
sudo systemctl enable myapp

# Both
sudo systemctl enable --now myapp

# Remove boot startup
sudo systemctl disable myapp
```

Mental model:

```text
             systemctl
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
     start               enable
       ↓                   ↓
     NOW                  BOOT
```
