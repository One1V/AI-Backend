
# Q85 — How do you run a Node.js app as a `systemd` service?

This is where the previous questions come together.

Instead of manually doing:

```bash
node server.js
```

you'll configure Linux to manage your Express application.

---

# 1. Your application

Suppose your server is:

```text
/home/ayush/myapp/
├── server.js
├── package.json
├── package-lock.json
└── .env
```

Your `server.js` contains:

```javascript
const express = require("express");

const app = express();

app.get("/", (req, res) => {
    res.send("Backend is running");
});

app.listen(5000, () => {
    console.log("Server running on port 5000");
});
```

Normally you would run:

```bash
node server.js
```

Instead, we'll create a Linux service.

---

# 2. Create the service file

Create:

```bash
sudo nano /etc/systemd/system/myapp.service
```

You'll write something like:

```ini
[Unit]
Description=My Express Backend
After=network.target

[Service]
User=ayush
WorkingDirectory=/home/ayush/myapp
ExecStart=/usr/bin/node server.js
Restart=always
Environment=NODE_ENV=production

[Install]
WantedBy=multi-user.target
```

Now let's understand it.

---

# 3. `[Unit]`

```ini
[Unit]
Description=My Express Backend
After=network.target
```

### `Description`

Just describes the service.

```text
My Express Backend
```

### `After=network.target`

Tells systemd that this service should be started **after the network target is available**.

Conceptually:

```text
Linux boot
   ↓
Network setup
   ↓
Your Node service
```

---

# 4. `[Service]`

This is the most important section.

```ini
[Service]
User=ayush
WorkingDirectory=/home/ayush/myapp
ExecStart=/usr/bin/node server.js
Restart=always
Environment=NODE_ENV=production
```

---

## `User`

```ini
User=ayush
```

This tells systemd:

> Run the application as the `ayush` user.

This is important for security.

You generally don't want your Node application running as `root` unnecessarily.

---

# 5. `WorkingDirectory`

```ini
WorkingDirectory=/home/ayush/myapp
```

This tells systemd:

> Treat this directory as the application's working directory.

So when it executes:

```text
server.js
```

systemd knows where that file is.

---

# 6. `ExecStart`

```ini
ExecStart=/usr/bin/node server.js
```

This tells systemd:

> **This is the command used to start my application.**

Conceptually:

```text
systemd
   ↓
ExecStart
   ↓
/usr/bin/node server.js
   ↓
Express
```

You should verify the actual Node path on your server with:

```bash
which node
```

For example, it might return:

```text
/usr/bin/node
```

If Node was installed using another method, the path can be different.

---

# 7. `Restart=always`

```ini
Restart=always
```

This tells systemd to restart the service if it exits.

Conceptually:

```text
Node
 ↓
CRASH ❌
 ↓
systemd
 ↓
Restart
 ↓
Node
```

This is extremely useful for production applications.

There are also other restart policies, such as:

```ini
Restart=on-failure
```

which is often a more precise choice when you only want restarts after failures.

---

# 8. `[Install]`

```ini
[Install]
WantedBy=multi-user.target
```

This is associated with enabling the service during boot.

When you run:

```bash
sudo systemctl enable myapp
```

systemd uses this installation relationship to determine how the service should be hooked into the boot process.

---

# 9. Tell systemd about the new service

After creating or modifying the service file:

```bash
sudo systemctl daemon-reload
```

This tells systemd:

> "I've changed the service configuration. Reload the unit definitions."

This does **not** restart your Node application by itself.

---

# 10. Start the application

Now:

```bash
sudo systemctl start myapp
```

Check:

```bash
sudo systemctl status myapp
```

You want:

```text
Active: active (running)
```

---

# 11. Enable it at boot

Now configure automatic startup:

```bash
sudo systemctl enable myapp
```

Or combine both:

```bash
sudo systemctl enable --now myapp
```

Now:

```text
VPS reboot
    ↓
Linux
    ↓
systemd
    ↓
myapp.service
    ↓
Node.js
    ↓
Express :5000
```

---

# 12. Check your API

Test locally on the server:

```bash
curl http://127.0.0.1:5000
```

You might get:

```text
Backend is running
```

Then if Nginx is configured:

```text
Browser
   ↓
Nginx :80/443
   ↓
Express :5000
```

---

# 13. What about `.env`?

This connects directly to the Linux permissions question you asked earlier.

Suppose:

```text
/home/ayush/myapp/.env
```

contains:

```text
MONGO_URI=...
JWT_SECRET=...
```

Your Node process needs permission to read it.

If:

```ini
User=ayush
```

then Node runs as `ayush`.

Linux checks:

```text
Node process
    ↓
tries to read .env
    ↓
Linux permission check
    ↓
Allowed?
```

If allowed:

```text
.env → read successfully
```

If not:

```text
Error: EACCES: permission denied
```

This is why the `User=` field matters.

---

# 14. View application logs

One of the biggest benefits of systemd is integration with `journalctl`.

Run:

```bash
sudo journalctl -u myapp
```

To follow logs live:

```bash
sudo journalctl -u myapp -f
```

If your Node application prints:

```javascript
console.log("Server started");
```

you can see it through the journal.

---

# 15. Restart after code changes

Suppose:

```bash
git pull origin main
```

updates your application.

Then:

```bash
sudo systemctl restart myapp
```

Check:

```bash
sudo systemctl status myapp
```

And:

```bash
sudo journalctl -u myapp -n 50
```

So your deployment workflow becomes:

```text
GitHub
   ↓
git pull
   ↓
Updated application
   ↓
systemctl restart myapp
   ↓
Node.js
   ↓
Express
```

# 🧠 Interview Answer

If asked:

> **"How would you run a Node.js application as a systemd service?"**

A strong answer:

> **"I'd create a unit file under `/etc/systemd/system/`, define the user, working directory, start command, and restart policy. Then I'd run `systemctl daemon-reload`, start the service with `systemctl start`, and enable it with `systemctl enable` so it starts automatically after reboot. I'd use `systemctl status` and `journalctl -u` to monitor it."**

The commands:

```bash
sudo nano /etc/systemd/system/myapp.service

sudo systemctl daemon-reload

sudo systemctl enable --now myapp

sudo systemctl status myapp

sudo journalctl -u myapp -f
```
