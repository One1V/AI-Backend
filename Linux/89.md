
# Q89 — How does Git fit into deployment?

Git is what lets you **move and update your application code between your development machine, GitHub, and your production server**.

The key idea is:

```text
Developer
   ↓
Git commit
   ↓
GitHub
   ↓
Production Server
   ↓
git pull
   ↓
Updated application
```

---

# 1. Development stage

You write your MERN application on your laptop:

```text
myapp/
├── frontend/
├── backend/
├── package.json
└── ...
```

You initialize Git:

```bash
git init
```

Then:

```bash
git add .
git commit -m "Initial commit"
```

And push:

```bash
git push origin main
```

Now your code is stored in a remote Git repository.

---

# 2. Server gets the application

On your Ubuntu VPS:

```bash
git clone <repository>
```

Now:

```text
GitHub
   ↓
git clone
   ↓
Ubuntu VPS
   ↓
Application
```

You don't need to manually copy every file using SCP every time.

---

# 3. What happens when you change your code?

Suppose you fix a bug:

```javascript
app.get("/api/users", ...)
```

You test it locally.

Then:

```bash
git add .
git commit -m "Fix users API"
git push origin main
```

Now GitHub contains the new version.

But **your VPS still has the old version**.

This is important.

```text
Laptop → GitHub ✅
VPS    → old code ❌
```

---

# 4. Update the production server

SSH into the VPS:

```bash
ssh ubuntu@SERVER_IP
```

Go to the project:

```bash
cd ~/myapp
```

Then:

```bash
git pull origin main
```

Now:

```text
GitHub
   ↓
git pull
   ↓
VPS gets new code
```

---

# 5. But `git pull` isn't always the final step

Suppose your backend code changed.

You pull:

```bash
git pull origin main
```

Your files are updated.

But the currently running Node process may still be running with the previous process state.

So restart the service:

```bash
sudo systemctl restart myapp
```

Then:

```bash
sudo systemctl status myapp
```

So a basic deployment update becomes:

```text
Developer
    ↓
git commit
    ↓
git push
    ↓
GitHub
    ↓
SSH into VPS
    ↓
git pull
    ↓
Updated code
    ↓
systemctl restart myapp
    ↓
New Node process
```

---

# 6. What if dependencies changed?

Suppose you install a new package locally:

```bash
npm install bcrypt
```

Your:

```text
package.json
package-lock.json
```

change.

You commit and push them:

```bash
git add package.json package-lock.json
git commit -m "Add bcrypt"
git push
```

On the server:

```bash
git pull
```

Then install dependencies:

```bash
npm install
```

Then:

```bash
sudo systemctl restart myapp
```

So:

```text
package.json changed
       ↓
git pull
       ↓
npm install
       ↓
restart application
```

---

# 7. What about `.env`?

This is **very important**.

You generally don't want:

```text
.env
```

containing production secrets to be committed to GitHub.

Your `.gitignore` might contain:

```text
.env
node_modules/
```

So:

```text
GitHub
 ├── source code
 ├── package.json
 └── .env ❌

VPS
 ├── source code
 ├── package.json
 └── .env ✅
```

The production server has its own environment configuration.

---

# 8. Why Git is useful for deployment

Imagine you deployed:

```text
Version 1
```

Then:

```text
Version 2
```

Then:

```text
Version 3
```

Git maintains the history:

```text
V1
 ↓
V2
 ↓
V3
```

You can inspect changes:

```bash
git log
```

and:

```bash
git diff
```

This gives you **version control**, which is extremely useful during deployment.

---

# 9. Rollback

Suppose you deploy:

```text
V3
```

and suddenly production breaks.

Because Git tracks previous commits, you can identify a previous working version.

For example:

```bash
git log --oneline
```

might show:

```text
a31f2c1 Fix authentication
72b8e41 Add payment API
19cd812 Initial deployment
```

You can then restore a known-good version using appropriate Git workflow, for example by checking out a specific commit for an emergency rollback.

After restoring the desired code:

```bash
sudo systemctl restart myapp
```

This is one of the major advantages of version-controlled deployments.

---

# 10. Git is NOT the deployment system itself

This is an important distinction.

Git handles:

```text
Version control
Code history
Branches
Commits
Merging
```

It doesn't inherently mean:

> "Deploy this application to production."

A deployment process can **use Git**.

For example:

```text
GitHub
   ↓
git pull
   ↓
systemd
   ↓
Node
```

Or a more advanced setup:

```text
Developer
   ↓
Git push
   ↓
GitHub
   ↓
CI/CD pipeline
   ↓
Build + Test
   ↓
Deploy
   ↓
Production
```

---

# 11. Manual deployment vs CI/CD

### Manual

You do:

```bash
git push
```

Then SSH:

```bash
ssh ubuntu@server
```

Then:

```bash
git pull
npm install
sudo systemctl restart myapp
```

This is fine for learning and small projects.

---

### CI/CD

A pipeline can automate the process:

```text
Developer
    ↓
git push
    ↓
GitHub
    ↓
CI/CD
    ↓
Tests
    ↓
Build
    ↓
Deploy
    ↓
Production
```

This is what you'll encounter in more mature production environments.

# 🧠 Interview Answer

If asked:

> **"How does Git fit into deployment?"**

Say:

> **"Git provides version control for the application code. During a basic deployment, I can clone the repository onto the server, and when new code is pushed, pull the latest changes onto the server. If dependencies change, I update them, then restart the application through a process manager such as systemd or PM2. In a mature setup, this process can be automated using CI/CD."**

That's a strong answer.
