
# Q90 — How do you pull updates from GitHub on a production server?

This is basically the **practical version of Q89**.

Suppose your Express application is already deployed on an Ubuntu VPS:

```text
GitHub
   ↓
Ubuntu VPS
   ↓
Nginx
   ↓
Express
```

You make a change locally and push it to GitHub. Now you need to update the production server.

---

## 1. Developer pushes new code

On your laptop:

```bash
git add .
git commit -m "Fix login API"
git push origin main
```

Now:

```text
Your Laptop
     ↓
   git push
     ↓
   GitHub
```

GitHub contains the latest version.

---

# 2. SSH into the production server

```bash
ssh ayush@SERVER_IP
```

Now you're inside your Ubuntu server.

Check where your application is:

```bash
cd ~/myapp
```

---

# 3. Check the current Git status

Before pulling, it's good practice to run:

```bash
git status
```

You might see:

```text
On branch main
Your branch is behind 'origin/main' by 1 commit.
```

That tells you the remote repository has newer code.

---

# 4. Pull the latest code

Run:

```bash
git pull origin main
```

Conceptually:

```text
              GitHub
                 │
          latest version
                 │
                 ▼
             git pull
                 │
                 ▼
           Ubuntu VPS
                 │
             new code
```

You should see something like:

```text
Updating abc1234..def5678
Fast-forward
 backend/server.js | 10 +++++-----
```

---

# 5. What if dependencies changed?

Suppose your developer added a package:

```bash
npm install bcrypt
```

That changes:

```text
package.json
package-lock.json
```

After:

```bash
git pull origin main
```

run:

```bash
npm install
```

This makes the server's installed dependencies match the project.

A common update flow is:

```bash
git pull origin main
npm install
```

But **only run `npm install` when dependencies may have changed**; blindly reinstalling every deployment isn't always necessary.

---

# 6. Restart the backend

If your Node application is managed by systemd:

```bash
sudo systemctl restart myapp
```

Then check:

```bash
sudo systemctl status myapp
```

You want:

```text
Active: active (running)
```

So the complete flow is:

```text
Developer
    ↓
git push
    ↓
GitHub
    ↓
SSH
    ↓
git pull
    ↓
Updated code
    ↓
npm install (if needed)
    ↓
systemctl restart myapp
    ↓
New Node process
```

---

# 7. Check the logs

If everything looks okay:

```bash
sudo journalctl -u myapp -n 50
```

For live logs:

```bash
sudo journalctl -u myapp -f
```

Then test the API:

```bash
curl http://localhost:5000/api/health
```

If you get:

```json
{
  "status": "OK"
}
```

your backend is responding.

---

# 8. What if `git pull` fails?

### Case 1 — Local changes on server

You might see:

```text
error: Your local changes would be overwritten by merge
```

Check:

```bash
git status
```

This means somebody changed files directly on the server.

**Don't blindly run `git reset --hard`** because you could destroy those changes.

First determine whether those changes are important.

---

### Case 2 — Merge conflict

Git may report a conflict.

You need to resolve it before the application can be safely updated.

---

### Case 3 — Authentication problem

You might get:

```text
Permission denied
```

or an authentication error.

The server needs appropriate access to the Git repository, commonly through SSH deploy keys or another supported authentication mechanism.

---

# 9. What about `.env`?

This is important.

Suppose GitHub contains:

```text
server.js
package.json
package-lock.json
```

but:

```text
.env
```

is ignored.

Your VPS has:

```text
myapp/
├── server.js
├── package.json
├── package-lock.json
└── .env
```

When you run:

```bash
git pull origin main
```

your production `.env` remains on the server because it isn't tracked by Git.

That's exactly what you generally want.

```text
GitHub
 ├── Code
 ├── package.json
 └── .env ❌

VPS
 ├── Code
 ├── package.json
 └── .env ✅
```

---

# 10. What if the frontend changed?

Suppose your React frontend is also deployed on the VPS.

You might:

```bash
git pull origin main
```

Then:

```bash
cd frontend
npm install
npm run build
```

This creates a new production build, commonly:

```text
dist/
```

Nginx serves that build.

So:

```text
GitHub
   ↓
git pull
   ↓
React source
   ↓
npm run build
   ↓
dist/
   ↓
Nginx
```

---

# 11. Complete MERN update

Suppose you changed both frontend and backend.

A simplified deployment might look like:

```bash
cd ~/myapp

git pull origin main

cd frontend
npm install
npm run build

cd ../backend
npm install

sudo systemctl restart myapp

sudo systemctl status myapp
```

Then test:

```bash
curl http://localhost:5000/api/health
```

And access your domain through the browser.

---

# 12. Important production warning

Don't think:

> "Production server = just `git pull`."

Real production deployment can involve:

```text
Git
 ↓
Testing
 ↓
Build
 ↓
Dependencies
 ↓
Environment configuration
 ↓
Database migrations
 ↓
Application restart
 ↓
Health checks
 ↓
Monitoring
```

For a small personal project, manual deployment is fine.

For larger systems, you'd normally automate much of this using **CI/CD**.

---

# 🧠 Interview Answer

If asked:

> **"How would you update an application deployed on an Ubuntu server from GitHub?"**

Say:

> **"I'd SSH into the server, go to the application's directory, check the Git status, and run `git pull origin main`. If dependencies changed, I'd run `npm install`, rebuild the frontend if necessary, and restart the backend using systemd or PM2. Finally, I'd check the service status and logs and perform a health check."**

That's a very good junior backend answer.
