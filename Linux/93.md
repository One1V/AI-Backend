
# Q93 — Backup and Restore Basics

This question is about one simple production principle:

> **If your server or database fails, how do you recover your data?**

Imagine your MERN application is running perfectly:

```text
Browser
   ↓
Nginx
   ↓
Express
   ↓
MongoDB
```

Then your VPS suddenly crashes.

Your application code can be redeployed from GitHub, but what about:

```text
Users
Orders
Posts
Payments
Profiles
```

That's where **backups** matter.

---

# 1. What is a backup?

A backup is a **separate copy of important data** that can be used to recover from loss or corruption.

For example:

```text
Production MongoDB
       │
       │ backup
       ▼
Backup storage
```

If production data is lost:

```text
Backup
  ↓
Restore
  ↓
Database
```

---

# 2. What should you back up?

For a typical backend:

### Database

Most important:

```text
MongoDB
```

because it contains your actual application data.

### Application configuration

Potentially:

```text
.env
Nginx configuration
systemd service files
```

But **secrets should be handled securely**, not simply copied into an insecure backup location.

### User-uploaded files

If your application allows:

```text
Profile pictures
PDFs
Documents
Videos
```

those also need a backup strategy.

---

# 3. Git is already a kind of backup — but not for everything

Your source code is stored in Git:

```text
GitHub
   ↓
Source code
```

So if your VPS dies:

```text
VPS ❌
```

you can deploy the application again:

```text
GitHub
   ↓
New VPS
   ↓
Application
```

But Git usually doesn't contain your production database.

So:

```text
Code
 → Git

Database
 → Database backup
```

This distinction is extremely important.

---

# 4. Example: MongoDB backup

MongoDB provides tools such as:

```bash
mongodump
```

A basic example:

```bash
mongodump --uri="mongodb://localhost:27017/myapp" --out=/backup/myapp
```

This creates a backup of the database.

Conceptually:

```text
MongoDB
   ↓
mongodump
   ↓
/backup/myapp
```

To restore, MongoDB provides:

```bash
mongorestore
```

For example:

```bash
mongorestore --uri="mongodb://localhost:27017/myapp" /backup/myapp
```

The exact command depends on your MongoDB deployment and authentication settings.

---

# 5. Don't keep the only backup on the same VPS

This is a **very important production concept**.

Bad:

```text
VPS
├── Application
├── MongoDB
└── Backup
```

What happens if the VPS's disk dies?

```text
VPS ❌
Database ❌
Backup ❌
```

You've lost everything.

Better:

```text
              Production VPS
                    │
                    │ backup
                    ▼
             Separate storage
```

For example, backups can be stored in separate cloud/object storage or another independent system.

---

# 6. Backup frequency

How often should you backup?

It depends on the application.

For example:

```text
Low-value personal project
→ occasional backup

Important application
→ daily backup

High-value production system
→ potentially much more frequent backups
```

The important concept is:

> **Backup frequency should match how much data you can afford to lose.**

---

# 7. Automated backups

You don't want to SSH into the server every day and type:

```bash
mongodump ...
```

Instead, automation can run backups periodically.

Linux provides tools such as:

```text
cron
```

or you can use backup features provided by your database/cloud provider.

Conceptually:

```text
Every night
    ↓
Backup job
    ↓
MongoDB dump
    ↓
Remote backup storage
```

---

# 8. Backup vs Restore

These are different operations.

### Backup

```text
Production
    ↓
Copy data
    ↓
Backup storage
```

### Restore

```text
Backup storage
    ↓
Recover data
    ↓
Production database
```

---

# 9. Real example

Imagine your application has:

```text
10,000 users
```

MongoDB contains:

```text
users
orders
posts
```

At 2 AM:

```text
Database corruption ❌
```

Without backup:

```text
Data → Lost
```

With backup:

```text
Backup
  ↓
mongorestore
  ↓
MongoDB
  ↓
Application
```

The application can recover.

---

# 10. What about the VPS itself?

Some VPS providers offer **server snapshots**.

A snapshot can capture the state of a server at a point in time.

Conceptually:

```text
VPS
 ↓
Snapshot
 ↓
Stored copy
```

If the server is damaged:

```text
Snapshot
   ↓
Restore
   ↓
VPS
```

Snapshots are useful, but they aren't necessarily a substitute for a proper database backup strategy.

---

# 11. Backup strategy for your MERN project

For the type of backend project you're learning, a sensible architecture is:

```text
                 Production
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      Code        MongoDB      Uploads
        │            │            │
        ↓            ↓            ↓
     GitHub       Backups     File backup
                     │
                     ↓
              Separate storage
```

So if the VPS disappears:

```text
VPS ❌
 │
 ├── Code → GitHub ✅
 ├── Database → Backup ✅
 └── Uploads → Backup ✅
```

You can rebuild the server.

---

# 12. The 3-2-1 backup principle

You may hear about the **3-2-1 rule**:

```text
3 copies of data
2 different types of storage
1 copy off-site
```

For example:

```text
Original database
      +
Local backup
      +
Remote backup
```

This reduces the risk of a single failure destroying everything.

---

# 13. Restore testing is important

Having a backup doesn't automatically mean you're safe.

Imagine:

```text
Backup created
     ↓
Everything looks fine
```

But when you actually try:

```text
mongorestore
```

it fails.

Therefore:

> **Backups should be periodically tested by performing restores.**

This is a very good production mindset.

---

# 🧠 Interview Answer

If asked:

> **"How would you back up a MERN application's data?"**

Say:

> **"I'd back up the database separately from the application source code. The source code is version-controlled in Git, while MongoDB data requires database backups such as `mongodump` or managed database backups. I'd store backups independently from the production server, automate them according to the application's recovery requirements, and periodically test restoring them."**

That's a strong answer.

---

# 🔑 Remember this

```text
GitHub
   ↓
Code backup

MongoDB
   ↓
Database backup

Uploads
   ↓
File backup

        ↓

Separate backup storage
        ↓
     Recovery
```

The biggest mistake to avoid is:

> **"My code is on GitHub, so my whole application is backed up."**

Your **database and user-uploaded data aren't automatically protected just because your source code is in Git.**
