
# Q97 — Debug: "Port 5000 already in use"

This is a **very common backend/Linux problem** and a great interview troubleshooting question.

Suppose you start your Express application:

```bash
node server.js
```

and get:

```text
Error: listen EADDRINUSE: address already in use :::5000
```

What does it mean?

---

# 1. What does `EADDRINUSE` mean?

It means:

> **Another process is already using port 5000.**

You wanted:

```text
Node.js
   ↓
Port 5000
```

But Linux already has:

```text
Another Process
   ↓
Port 5000
```

So Node cannot bind to that port.

---

# 2. Real example

Suppose you accidentally started your server twice.

First:

```bash
node server.js
```

It starts successfully:

```text
Server running on port 5000
```

Now you open another terminal and run:

```bash
node server.js
```

The second process tries:

```text
Node
 ↓
Bind port 5000
```

But:

```text
Port 5000
 ↓
Already occupied
 ↓
❌ EADDRINUSE
```

---

# 3. First thing: find who is using port 5000

Use:

```bash
sudo lsof -i :5000
```

You might get:

```text
COMMAND   PID   USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
node     2345  ayush   20u  IPv6 ...          TCP *:5000 (LISTEN)
```

Important information:

```text
COMMAND → node
PID     → 2345
PORT    → 5000
```

Now you know exactly which process is using it.

---

# 4. Another useful command: `ss`

You can also use:

```bash
sudo ss -ltnp | grep :5000
```

You might see:

```text
LISTEN 0 511 0.0.0.0:5000 0.0.0.0:* users:(("node",pid=2345))
```

Meaning:

```text
LISTEN
   ↓
Something is accepting connections
   ↓
Port 5000
   ↓
Node process
   ↓
PID 2345
```

This connects directly to what you learned in the networking module.

---

# 5. Find the process

You can inspect the PID:

```bash
ps -p 2345 -f
```

Example:

```text
UID     PID   CMD
ayush  2345   node server.js
```

Now you know:

> Node.js process 2345 is occupying port 5000.

---

# 6. Should you immediately `kill -9` it?

**No.**

This is an important production habit.

First try a normal termination:

```bash
kill 2345
```

This normally sends:

```text
SIGTERM
```

Give the application a chance to shut down cleanly.

Then check:

```bash
sudo ss -ltnp | grep :5000
```

If nothing appears, port 5000 is free.

---

# 7. Then start your application

```bash
node server.js
```

Now:

```text
Port 5000
   ↓
Available
   ↓
Node
   ↓
Listening
```

---

# 8. What if `kill` doesn't work?

If the process refuses to terminate, you can use:

```bash
kill -9 2345
```

This sends:

```text
SIGKILL
```

The OS forcibly terminates the process.

But remember:

```text
kill PID
     ↓
SIGTERM
     ↓
Graceful shutdown

kill -9 PID
     ↓
SIGKILL
     ↓
Forceful termination
```

Don't make `kill -9` your default solution.

---

# 9. What if PM2/systemd is managing the application?

This is where your deployment knowledge becomes important.

Suppose:

```text
systemd
   ↓
myapp.service
   ↓
Node
   ↓
5000
```

You shouldn't manually kill the Node process and then start another copy.

Instead:

```bash
sudo systemctl restart myapp
```

Check:

```bash
sudo systemctl status myapp
```

Similarly, if you're using PM2:

```bash
pm2 list
```

Then:

```bash
pm2 restart myapp
```

The process manager should control the application lifecycle.

---

# 10. Another possibility: your application is already running correctly

This is a **very important real-world situation**.

Suppose you deployed your application with systemd:

```text
systemd
   ↓
Node :5000
```

Then you SSH into the server and run:

```bash
node server.js
```

You get:

```text
EADDRINUSE
```

You might think:

> "Something is broken!"

But actually:

```text
systemd
   ↓
Node
   ↓
5000
```

is **already running**.

You accidentally tried to create a second instance.

Check:

```bash
sudo systemctl status myapp
```

If it's active:

```text
Active: active (running)
```

then don't start another Node process manually.

---

# 11. Another possibility: old process

Suppose you previously ran:

```bash
node server.js
```

Then closed your terminal incorrectly or left it running.

The Node process may still exist:

```text
Node
 ↓
PID 2345
 ↓
5000
```

Find it:

```bash
sudo lsof -i :5000
```

Then terminate it if appropriate:

```bash
kill 2345
```

---

# 12. What about changing the port?

You could change:

```javascript
const PORT = 5000;
```

to:

```javascript
const PORT = 5001;
```

Then:

```text
Node
 ↓
5001
```

But this isn't always the right solution.

If Nginx is configured:

```nginx
proxy_pass http://127.0.0.1:5000;
```

and you change Express to:

```text
5001
```

Nginx still tries:

```text
Nginx
 ↓
5000 ❌
```

while Express is on:

```text
5001
```

You'd have to update Nginx too.

So **first find why 5000 is occupied** instead of randomly changing the port.

---

# 13. Complete debugging flow

Memorize this:

```text
EADDRINUSE
     │
     ▼
Port 5000 already in use
     │
     ▼
Find process
     │
     ├── lsof -i :5000
     │
     └── ss -ltnp | grep :5000
     │
     ▼
Get PID
     │
     ▼
Identify process
     │
     └── ps -p PID -f
     │
     ▼
Is it supposed to be running?
     │
   ┌─┴───────────────┐
   │                 │
  Yes               No
   │                 │
Use/restart        kill PID
service             │
                    ▼
                 Start app
```

---

# 14. Real production example

Suppose your architecture is:

```text
Internet
   ↓
Nginx :443
   ↓
Express :5000
```

You receive:

```text
EADDRINUSE :5000
```

You investigate:

```bash
sudo ss -ltnp | grep :5000
```

Output:

```text
users:(("node",pid=2451))
```

Then:

```bash
ps -p 2451 -f
```

Output:

```text
node server.js
```

Now check:

```bash
sudo systemctl status myapp
```

If it says:

```text
active (running)
```

you realize:

> **The production server is already running. I shouldn't start another instance manually.**

That's exactly the kind of reasoning an interviewer wants.

---

# 🧠 Interview Answer

If the interviewer asks:

> **"Your Node.js application says `EADDRINUSE: port 5000 already in use`. How would you debug it?"**

Answer:

> **"First I'd identify which process is listening on port 5000 using `ss -ltnp` or `lsof -i :5000`. I'd get the PID and inspect the process using `ps`. Then I'd determine whether that process is supposed to be running. If it's an existing application managed by systemd or PM2, I'd use the process manager rather than starting another instance. If it's an unwanted process, I'd terminate it gracefully with SIGTERM and only use SIGKILL if necessary."**

That's an excellent junior backend/Linux answer.

