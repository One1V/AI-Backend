
# Q98 — Debug: `Permission denied`

This is another **very common Linux + backend deployment problem**.

You've already encountered this type of problem while working with Nginx, so this one is especially important for you.

Suppose you run:

```bash
cat /var/www/myapp/index.html
```

and Linux says:

```text
Permission denied
```

Or Nginx gives:

```text
500 Internal Server Error
```

with a log like:

```text
permission denied
```

The question is:

> **Why is Linux refusing access, and how do you debug it?**

---

# 1. First understand the permission model

Linux generally evaluates permissions using:

```text
User
Group
Others
```

For example:

```bash
ls -l index.html
```

might show:

```text
-rw-r--r-- 1 ayush ayush 1024 Aug 10 index.html
```

Break this down:

```text
-rw-r--r--
 │ │   │
 │ │   └── Others
 │ └────── Group
 └──────── Owner
```

Permissions:

```text
r = read
w = write
x = execute
```

---

# 2. Example

Suppose:

```text
-rw-r--r--
```

means:

```text
Owner   → rw-
Group   → r--
Others  → r--
```

So:

```text
Owner
→ read + write

Group
→ read

Others
→ read
```

---

# 3. Why does "Permission denied" happen?

Imagine:

```text
Nginx
   ↓
/var/www/myapp/index.html
```

But the file is:

```text
-rw------- ayush ayush index.html
```

That means:

```text
Owner → read/write
Group → nothing
Others → nothing
```

If Nginx is running as another user, it may not be allowed to read the file.

Result:

```text
Nginx
  ↓
index.html
  ↓
❌ Permission denied
```

---

# 4. First command: `ls -l`

When you see permission errors, start with:

```bash
ls -l filename
```

For example:

```bash
ls -l /var/www/myapp/index.html
```

You might see:

```text
-rw------- 1 ayush ayush index.html
```

Now you know the permissions are extremely restrictive.

---

# 5. But don't only check the file

This is a **very important detail**.

Suppose:

```text
/var/www/myapp/index.html
```

has:

```text
-rw-r--r--
```

It looks readable.

But Nginx still gets:

```text
Permission denied
```

Why?

Because Linux also checks the **directories in the path**.

For example:

```text
/
└── var
    └── www
        └── myapp
            └── index.html
```

Nginx needs appropriate permissions to **traverse** the directories.

Directory traversal requires:

```text
x
```

permission on directories.

---

# 6. File `r` vs directory `x`

This is a common interview follow-up.

For a **file**:

```text
r → read contents
w → modify contents
x → execute
```

For a **directory**:

```text
r → list directory contents
w → create/delete/rename entries
x → traverse/access entries
```

So:

```text
Directory
   ↓
x permission
   ↓
Can traverse it
```

---

# 7. Real Nginx example

Suppose:

```text
/var/www/myapp/index.html
```

Nginx runs as:

```text
www-data
```

You can check:

```bash
ps aux | grep nginx
```

You may see workers running as:

```text
www-data
```

Now imagine:

```text
/var/www/myapp
```

has:

```text
drwx------ ayush ayush myapp
```

Then:

```text
ayush
 ↓
Can access

www-data
 ↓
Cannot traverse
 ↓
❌ Permission denied
```

Even if:

```text
index.html
```

itself is readable.

---

# 8. `namei` is useful

A very useful debugging command is:

```bash
namei -l /var/www/myapp/index.html
```

It shows permissions for each component of the path.

Conceptually:

```text
/
 ↓
var
 ↓
www
 ↓
myapp
 ↓
index.html
```

This helps you find **which directory is blocking access**.

---

# 9. `chmod`

You can change permissions with:

```bash
chmod
```

For example:

```bash
chmod 644 index.html
```

means:

```text
Owner  → rw-
Group  → r--
Others → r--
```

For directories, a common permission is:

```bash
chmod 755 myapp
```

meaning:

```text
Owner  → rwx
Group  → r-x
Others → r-x
```

This allows users/processes to traverse and read the directory while only the owner can modify it.

But:

> **Don't blindly use `chmod 777`.**

---

# 10. Why `chmod 777` is a bad solution

You might see beginners solve everything with:

```bash
chmod 777 file
```

This gives:

```text
Owner  → rwx
Group  → rwx
Others → rwx
```

Now practically everyone can read, modify, and execute it.

That's usually far more permission than necessary.

Production principle:

> **Give a process only the permissions it actually needs.**

This is the **principle of least privilege**.

---

# 11. `chown`

Sometimes the problem isn't the permission bits.

The ownership is wrong.

Check:

```bash
ls -l
```

Suppose:

```text
-rw-r--r-- 1 root root index.html
```

You may need to change ownership depending on how your deployment is structured.

Command:

```bash
sudo chown user:group index.html
```

For example:

```bash
sudo chown ayush:ayush index.html
```

Be careful when changing ownership of system-managed files.

---

# 12. Your earlier Nginx problem

Remember the situation you encountered:

```text
Nginx
   ↓
index.html
   ↓
Permission denied
```

The correct debugging approach is:

```text
Permission denied
       ↓
Who is accessing?
       ↓
What user does Nginx run as?
       ↓
Check file permissions
       ↓
Check directory permissions
       ↓
Check ownership
       ↓
Fix only the required permission
```

Not:

```text
Permission denied
       ↓
chmod 777 everything ❌
```

---

# 13. `.env` is a different case

Suppose your application has:

```text
.env
```

with:

```text
MONGO_URI=...
JWT_SECRET=...
```

You **don't** want Nginx or normal users to freely read it.

For example:

```bash
chmod 600 .env
```

gives:

```text
Owner → read/write
Group → nothing
Others → nothing
```

This is much safer for a secret file.

The Node process must run as a user that can read it.

---

# 14. How does Linux decide?

Suppose:

```text
.env
owner = ayush
group = ayush
permissions = 600
```

and Node runs as:

```text
ayush
```

Then:

```text
Node
 ↓
Running as ayush
 ↓
.env
 ↓
Owner permissions
 ↓
Read allowed
```

But if some unrelated user tries:

```text
bob
 ↓
.env
```

they don't get the owner's permission.

Result:

```text
Permission denied
```

---

# 15. `sudo` doesn't mean you should use it everywhere

You can do:

```bash
sudo cat /some/file
```

because root has elevated privileges.

But don't make your application run as root just to avoid permission problems.

Bad:

```text
Node
 ↓
root
```

Better:

```text
Node
 ↓
Dedicated/non-root user
```

This limits the damage if the application is compromised.

---

# 16. Production debugging flow

When you see:

```text
Permission denied
```

follow this:

```text
                 Permission denied
                        │
                        ▼
              Which process/user?
                        │
                        ▼
              Check ownership
                        │
                        ▼
              Check file permissions
                        │
                        ▼
            Check directory permissions
                        │
                        ▼
              Check parent directories
                        │
                        ▼
          Fix minimum required permission
```

Useful commands:

```bash
ls -l <file>
```

```bash
namei -l <path>
```

```bash
ps aux | grep nginx
```

```bash
ps aux | grep node
```

```bash
ls -ld <directory>
```

---

# 🧠 Interview Answer

If asked:

> **"How would you debug a Permission Denied error on a Linux server?"**

A strong answer:

> **"First I'd identify which process and user is trying to access the resource. Then I'd check the file's ownership and permissions using `ls -l`, and check the permissions of every directory in the path because directory traversal requires execute permission. I'd use `namei -l` if necessary. Then I'd fix the ownership or permissions with `chown` or `chmod`, giving only the minimum permissions required rather than using something like `chmod 777`."**

That's a **very solid backend/Linux interview answer**.

---

# 🔑 Commands to remember

```bash
# File permissions
ls -l file

# Directory permissions
ls -ld directory

# Permissions throughout path
namei -l /var/www/myapp/index.html

# Change permissions
chmod 644 file
chmod 755 directory

# Change ownership
sudo chown user:group file

# Find Nginx user/process
ps aux | grep nginx

# Find Node process
ps aux | grep node
```

### The key mental model:

```text
Linux permission
       ↓
Who are you?
       ↓
Owner / Group / Other
       ↓
What permission do you have?
       ↓
r / w / x
       ↓
Allowed or Permission Denied
```
