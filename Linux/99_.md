
# Q99 — Debug: "Server is Down"

This is one of the **most important practical backend troubleshooting questions**.

An interviewer may simply say:

> **"Your production server is down. What do you do?"**

Don't immediately restart everything.

A good backend engineer **diagnoses layer by layer**.

---

# 1. Start from the outside

Your architecture is:

```text
Browser
   ↓
DNS
   ↓
Internet
   ↓
VPS
   ↓
Nginx
   ↓
Express
   ↓
MongoDB
```

If the website is down, **any layer could be responsible**.

So troubleshoot from:

```text
Outside
   ↓
Network
   ↓
Server
   ↓
Nginx
   ↓
Application
   ↓
Database
```

---

# 2. First question: Is the server reachable?

Try:

```bash
ping SERVER_IP
```

But remember:

> A failed ping does **not necessarily mean the server is down**, because ICMP may be blocked by a firewall.

A better test is often:

```bash
ssh user@SERVER_IP
```

If SSH works:

```text
Internet
   ↓
Server
   ↓
Reachable ✅
```

So you know the VPS itself is probably alive.

---

# 3. Check the VPS

Once connected:

```bash
uptime
```

You might get:

```text
10:30:21 up 5 days, 3:21, 2 users, load average: 0.20, 0.30, 0.25
```

This tells you:

* How long the server has been running
* Current load information

Also:

```bash
free -h
```

for memory.

And:

```bash
df -h
```

for disk usage.

---

# 4. Check CPU

Use:

```bash
top
```

or:

```bash
htop
```

Suppose you discover:

```text
CPU → 100%
```

Maybe some process is consuming all available CPU.

Find processes:

```bash
ps aux --sort=-%cpu | head
```

Conceptually:

```text
Process A → 95% CPU
Process B → 2%
Process C → 1%
```

Now you've found a potential cause.

---

# 5. Check memory

Run:

```bash
free -h
```

Suppose:

```text
Mem:
total   4G
used    3.9G
free    100M
```

Memory pressure could cause processes to become unstable or be killed.

You can also:

```bash
ps aux --sort=-%mem | head
```

to identify memory-heavy processes.

---

# 6. Check disk space

Run:

```bash
df -h
```

Suppose:

```text
Filesystem      Size  Used Avail
/dev/sda1       20G   20G     0G
```

🚨 Disk is full.

This can cause serious problems.

For example:

```text
Nginx
 ↓
Can't write logs
 ↓
Application
 ↓
Can't write files
 ↓
Database
 ↓
Potential problems
```

Find large directories:

```bash
du -sh /*
```

Then investigate further.

---

# 7. Check Nginx

Now move up the application stack.

```bash
sudo systemctl status nginx
```

You might see:

```text
Active: active (running)
```

Good.

If you see:

```text
Active: failed
```

check:

```bash
sudo nginx -t
```

This checks the configuration.

Then:

```bash
sudo journalctl -u nginx -n 100
```

And:

```bash
sudo tail -f /var/log/nginx/error.log
```

---

# 8. Common Nginx problem

Suppose you changed:

```text
/etc/nginx/sites-available/default
```

and accidentally made a syntax error.

Then:

```bash
sudo nginx -t
```

might return something like:

```text
nginx: [emerg] unexpected "}"
```

Don't restart blindly.

Fix the configuration first.

Then:

```bash
sudo nginx -t
```

and only after it succeeds:

```bash
sudo systemctl reload nginx
```

---

# 9. Check whether Nginx is listening

Use:

```bash
sudo ss -ltnp | grep :443
```

and:

```bash
sudo ss -ltnp | grep :80
```

You want something like:

```text
LISTEN ... :443 ... nginx
```

If nothing is listening:

```text
Browser
   ↓
:443
   ↓
❌ Nobody listening
```

That's a strong clue.

---

# 10. Check Express

Suppose Nginx is working.

Next:

```bash
sudo systemctl status myapp
```

You might discover:

```text
Active: failed
```

Now inspect logs:

```bash
sudo journalctl -u myapp -n 100
```

You might find:

```text
Error: Cannot connect to MongoDB
```

or:

```text
EADDRINUSE
```

or:

```text
MODULE_NOT_FOUND
```

or:

```text
Permission denied
```

Now you've found the actual problem.

---

# 11. Check port 5000

Run:

```bash
sudo ss -ltnp | grep :5000
```

If nothing appears:

```text
Nginx
 ↓
127.0.0.1:5000
 ↓
❌ No process listening
```

That explains why Nginx can't reach Express.

If something else is listening:

```text
Port 5000
 ↓
Unexpected process
```

you have another problem to investigate.

---

# 12. Test Express directly

This is an extremely useful debugging technique.

From the VPS:

```bash
curl http://127.0.0.1:5000/api/health
```

Suppose:

```json
{
  "status": "OK"
}
```

Then:

```text
Express ✅
```

If that works but:

```bash
curl https://example.com/api/health
```

fails:

```text
Express ✅
Nginx ❌
```

Now you've narrowed the problem to Nginx/network/TLS rather than your Node application.

---

# 13. Test Nginx locally

You can also test:

```bash
curl http://localhost
```

If Nginx is configured correctly, it should return your expected response.

This helps separate:

```text
Internet problem
```

from:

```text
Server/application problem
```

---

# 14. Check MongoDB

Suppose:

```text
Nginx ✅
Express ✅
```

but API requests that require database access fail.

Now investigate MongoDB.

If using a local MongoDB:

```bash
sudo systemctl status mongod
```

If using MongoDB Atlas, check:

* Connection string
* Network access/IP allowlist
* Credentials
* Database availability

Your application logs may show something like:

```text
MongoServerSelectionError
```

That points toward the database/network layer.

---

# 15. Check environment variables

A surprisingly common production problem:

```text
.env
   ↓
Missing/incorrect
```

For example:

```text
MONGO_URI undefined
```

Then Express starts but fails when it tries to connect to MongoDB.

Check the application's environment/configuration carefully.

**Don't expose secrets in logs or commands you share publicly.**

---

# 16. Check DNS

Suppose:

```text
curl http://127.0.0.1:5000
```

works.

And:

```text
curl http://localhost
```

works.

But:

```text
example.com
```

doesn't work.

Then investigate DNS.

Check:

```bash
dig example.com
```

or:

```bash
nslookup example.com
```

You want the domain to resolve to the correct server IP.

---

# 17. Check firewall

Suppose Nginx is running:

```text
Nginx → active
```

and listening:

```text
:443 → LISTEN
```

but users can't connect externally.

Check firewall rules.

On Ubuntu, you may use:

```bash
sudo ufw status
```

You generally want the required ports allowed, such as:

```text
22  → SSH
80  → HTTP
443 → HTTPS
```

You usually **do not need to expose Express's port 5000 publicly** when Nginx is reverse-proxying to it locally.

---

# 18. Use logs

Logs are one of your best debugging tools.

### Nginx

```bash
sudo tail -f /var/log/nginx/error.log
```

### Application

```bash
sudo journalctl -u myapp -f
```

### System

```bash
sudo journalctl -xe
```

Don't just restart the server and hope.

**Find the error first.**

---

# 19. A real troubleshooting example

Suppose your website shows:

```text
502 Bad Gateway
```

Don't conclude:

> "Nginx is broken."

A 502 often means Nginx can't get a valid response from the upstream application.

Check:

```bash
sudo systemctl status myapp
```

You discover:

```text
myapp.service → failed
```

Then:

```bash
sudo journalctl -u myapp -n 100
```

shows:

```text
MongoServerSelectionError
```

Now your path is:

```text
Browser
   ↓
Nginx ✅
   ↓
Express ❌/unhealthy
   ↓
MongoDB ❌
```

That's much better than randomly restarting Nginx.

---

# 20. Your debugging decision tree

Memorize this:

```text
              SERVER DOWN?
                   │
                   ▼
            Can I SSH into it?
              /          \
            No            Yes
            │              │
      Network/VPS      Check resources
      investigation        │
                            ▼
                      CPU / RAM / Disk
                            │
                            ▼
                       Is Nginx up?
                         /      \
                       No        Yes
                       │          │
                 Check logs    Check Express
                                  │
                                  ▼
                            Port 5000?
                              /    \
                            No      Yes
                            │        │
                      Check app   Test API
                      service        │
                                     ▼
                              Check MongoDB
```

---

# 🧠 Interview Answer

If asked:

> **"Your production server is down. How would you debug it?"**

Give a structured answer:

> **"I'd troubleshoot layer by layer rather than immediately restarting everything. First I'd check whether I can SSH into the server and then check CPU, memory and disk usage. I'd verify that Nginx is running and listening on ports 80/443 and inspect its logs. Then I'd check the Node.js service using systemd, inspect its logs and verify that it's listening on the expected port, such as 5000. I'd test the application directly with curl to separate an Nginx problem from an application problem. Finally, I'd check the database connection, DNS and firewall if necessary."**

That's a **very strong practical answer**.

## 🎯 The most important principle

When a production server is down:

> **Don't restart everything blindly. Isolate the failing layer.**

```text
DNS
 ↓
Network
 ↓
Linux
 ↓
Nginx
 ↓
Express
 ↓
MongoDB
```

Once you can systematically walk through this chain, you're no longer just learning Linux commands—you are learning **production troubleshooting**.
